## 问题 — 为什么文件写入后还可能丢数据？

你写了 `f.write("hello")`，但数据可能还没真正写到磁盘——它在内存里的**页缓存**中。断电就丢了。

```python
f.write("hello")
f.flush()    # 刷到 OS 缓冲区
os.fsync(f.fileno())  # 强制写到磁盘 ← 这才真正安全
```

s09 Memory 系统需要保证写入持久化，这就是为什么它要用 `flush` + `fsync`。

## 核心概念

### 1. 磁盘 — 持久化存储

| | SSD | HDD |
|---|---|---|
| 原理 | 电子 NAND 闪存 | 磁头 + 旋转盘片 |
| 随机读取 | ~100µs | ~10ms (寻道) |
| 耐震动 | 优秀 | 脆弱 |
| 价格 | 较贵 | 便宜 |

Python 的 `open/read/write` 最终都变成磁盘 I/O。OS 会缓存写入，攒一批再落盘——这样性能好，但有丢数据风险。

### 2. 虚拟内存 — "每个程序都以为自己有 128GB 内存"

你电脑只有 16GB 物理内存，但同时跑了 Chrome + VS Code + Python + Docker。它们怎么共存？

**虚拟内存**给每个进程一个独立的、从 0 开始的地址空间。进程看到的地址是"假的"（虚拟地址），CPU 里的 MMU（内存管理单元）负责翻译成真实的物理地址。

**翻译过程**：

```
虚拟地址 0x7fff1234
    │
    ▼
MMU 查页表 (page table)
    │
    ├── 在内存里 → 翻译成物理地址 0x3a2b1234 → 读写
    │
    └── 不在内存 (被 swap 到磁盘) → 缺页中断
         → OS 从磁盘捞回来 → 更新页表 → 重试
```

- **页 (Page)**：虚拟内存的基本单位，通常 4KB
- **缺页 (Page Fault)**：访问的页不在物理内存里，要去磁盘找（~10ms 延迟）
- **Swap**：磁盘上划出来当假内存用的区域，物理内存不够时用

### 3. 文件系统 — 目录树 + inode

```
/home/user/project/           ← 绝对路径
├── s01_agent_loop/           ← 目录（也是一个文件）
│   ├── README.md             ← 普通文件
│   └── code.py
└── .env                      ← 隐藏文件
```

- **inode**：每个文件背后的数据结构，存文件大小、权限、数据块在磁盘上的位置。文件名只是指向 inode 的标签
- **文件描述符 (fd)**：进程追踪打开文件用的整数。0=stdin, 1=stdout, 2=stderr, 再打开从 3 开始

```python
fd = os.open("file.txt", os.O_RDONLY)  # fd = 3
os.read(fd, 100)
os.close(fd)
```

### 4. 路径遍历攻击

```python

```

## 小结

```
磁盘: 断电不丢，但比内存慢 10000 倍
      ↓

      ↓

      ↓

```
