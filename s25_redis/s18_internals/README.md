## 2. RESP 协议 — Redis 和客户端说的"语言"

### 2.1 什么是 RESP？

RESP（Redis Serialization Protocol）是 Redis 客户端和服务端通信的协议。它的设计原则是：

> **简单、快速、人类可读**

### 2.2 五种基本数据类型

```
RESP 用不同的前缀表示不同的数据类型:

+OK\r\n                → 简单字符串 (Simple String)    → 状态响应
-ERR message\r\n      → 错误 (Error)                  → 错误信息
:1\r\n                → 整数 (Integer)                → 数字响应
$5\r\nhello\r\n        → 批量字符串 (Bulk String)     → 字符串值
*3\r\n...              → 数组 (Array)                  → 多条数据
```

### 2.3 一个 SET 命令的 RESP 表示

```
客户端发送: SET name "小明"

RESP 编码:
  *3\r\n            ← 数组有 3 个元素
  $3\r\nSET\r\n     ← 第一个元素: 长度为 3 的字符串 "SET"
  $4\r\nname\r\n    ← 第二个元素: 长度为 4 的字符串 "name"
  $6\r\n小明\r\n    ← 第三个元素: 长度为 6 的字符串 "小明"

服务端回复:
  +OK\r\n           ← 简单字符串 "OK"

人类可读版本:
  *3
  $3
  SET
  $4
  name
  $6
  小明
```

### 2.4 为什么 RESP 重要？

```
理解 RESP 的好处:

1. 排查问题时可以用 telnet 或 nc 直接发 RESP 命令
2. 理解 Redis 的「逐行解析」方式 → 理解为什么它这么快
3. 知道响应格式 → 能读懂 redis-py 返回的原始数据类型
4. 了解协议开销 → 设计批量操作时能估算性能
```

> **小实验**：后面 code.py 会用原始 TCP 连接发送 RESP 数据，让你亲眼看到 REDIS 协议的"真面目"。

## 3. 单线程为什么这么快？

Redis 最让人惊讶的设计是：**它是单线程的**。在"多核为王"的今天，一个单线程的数据库凭什么能支撑每秒数十万的请求？

### 3.1 三大法宝

```
法宝一：I/O 多路复用（IO Multiplexing）

  传统阻塞 I/O:
    线程 1: 读取客户端 A → 等待 A 的请求 → 处理 → 返回
    线程 2: 读取客户端 B → 等待 B 的请求 → 处理 → 返回
    每个连接需要一个线程，线程切换开销大

  Redis 使用 epoll (Linux) / kqueue (macOS):
    一个线程同时监视所有客户端的连接
    只有某个客户端发来了数据，才去处理它
    没有数据时线程休眠 → 不占用 CPU

  类比:
    传统方式: 你在教室门口，每个学生配一个保安
             → 保安 A 只盯着学生 A，保安 B 只盯着学生 B
             → 学生 C 上厕所，保安 C 也在干等
    Redis 方式: 一个保安扫视整个教室
              → 谁举手就去处理谁
              → 没人举手就闭眼休息


法宝二：纯内存操作

  Redis 的所有数据都在内存中。
  内存读取速度：~50ns（纳秒）
  磁盘读取速度：~10ms（毫秒）
  差距：200,000 倍！

  所以即使单线程，内存操作也快得超乎想象。


法宝三：无锁设计

  多线程 = 需要锁 = 需要等待锁 = 性能下降
  单线程 = 不需要锁 = 没有竞争 = 极致性能

  每个命令都是原子操作——因为根本没有并发执行的命令！
```

### 3.2 单线程的代价

```
Redis 单线程不擅长的事情：

1. 大 Key 操作（KEYS *、LRANGE huge_list、SMEMBERS huge_set）
   → 这些命令执行期间,所有其他客户端都被阻塞
  
2. 慢查询（复杂的 Lua 脚本、MIGRATE、SORT）
   → 脚本运行 5 秒 = Redis 停止响应 5 秒

3. 高 CPU 消耗操作（频繁的哈希重哈希）
   → 单线程 = CPU 占用不能超过 100%

4. 多核利用
   → 一台服务器 64 核，Redis 只用一个
   → 解决：多实例部署（一台机器跑多个 Redis 实例）
```

> Redis 6.0 引入了**多线程 I/O**（用于网络读写），但命令执行仍然是单线程的。这不是矛盾——网络 I/O 用多线程加速，命令处理保持单线程的简单性。

## 4. 内存编码机制

Redis 对内存使用非常"吝啬"。它用多种编码方式来存储数据，**对用户透明**——你 SET/GET 时不用管底层编码。

### 4.1 String 的三种编码

| 编码 | 名称 | 条件 | 存储方式 |
|------|------|------|---------|
| `int` | 整数编码 | 值是整数（如 `123`），在 LONG 范围内 | 直接存为 long，不额外分配内存 |
| `embstr` | 嵌入式字符串 | 长度 ≤ 44 字节 | Redis 对象和字符串存在同一块内存 |
| `raw` | 原始字符串 | 长度 > 44 字节 | Redis 对象和字符串分开存储 |

```
SET key 123      → OBJECT ENCODING key → "int"      (8 字节)
SET key "hello"  → OBJECT ENCODING key → "embstr"   (< 44 字节)
SET key "a"*100  → OBJECT ENCODING key → "raw"      (> 44 字节)

为什么阈值是 44 字节？
  因为 Redis 对象头（16 字节）+ SDS 头（3 字节）+ 数据 + 结束符
  = 64 字节的 Jemalloc 最小分配单元
  数据 ≈ 64 - 16 - 3 - 1 = 44 字节
  超过 44 字节就要用两块内存了 → raw
```

### 4.2 Hash/Set/ZSet 的紧凑编码

```
小数据量 → 紧凑编码（省内存）
大数据量 → 常规编码（快操作）

Hash:
  < 512 个字段 + 字段长度 < 64 字节 → ziplist（压缩列表）
  > 512 个字段或字段长度 > 64 字节 → hashtable（哈希表）

Set:
  所有元素都是整数且 < 512 个 → intset（整数集合）
  否则 → hashtable（哈希表）

ZSet:
  < 128 个元素 → ziplist（压缩列表）
  > 128 个元素 → skiplist（跳表）+ hashtable
```

### 4.3 以 Hash 为例：ziplist → hashtable 的转换

```
小 Hash（用 ziplist 编码）:
  ┌────────────────────────────┐
  │  zlbytes │ zltail │ zllen  │
  │  field1 │ value1 │ field2  │
  │  value2 │ ...     │ zlend  │
  └────────────────────────────┘
  
  所有字段连续存储，像一个数组
  优点：省内存（几乎没有额外开销）
  缺点：查找是 O(n)，添加/删除需要内存搬移

当字段数或字段长度超过阈值:

大 Hash（用 hashtable 编码）:
  ┌────────────────────────────┐
  │  ┌─┐  ┌─┐  ┌─┐            │
  │  │ │→│ │→│ │  ...         │
  │  └─┘  └─┘  └─┘            │
  │  哈希表 + 链表解决冲突     │
  └────────────────────────────┘
  
  优点：查找 O(1)，添加/删除 O(1)
  缺点：有额外内存开销（空桶、指针）
```

## 5. 渐进式 rehash

### 5.1 为什么需要 rehash？

Hash 和 Set 用 hashtable 存储时，随着数据增加，哈希表的**负载因子**升高：

```
负载因子 = 元素数量 / 桶数量

负载因子 > 1 → 查找性能下降（冲突增多）
负载因子 > 5 → 可能需要扩容
```

扩容需要**更大的哈希表**和**重新哈希**。

### 5.2 普通 rehash 的问题

```
普通 rehash:
  ① 创建新哈希表（桶数翻倍）
  ② 遍历旧表所有元素
  ③ 重新计算每个元素的哈希值
  ④ 插入到新表
  ⑤ 释放旧表

问题：如果旧表有 1000 万个 key
      → 单线程要处理 1000 万次 rehash
      → Redis 在这期间不能处理任何请求！
      → 卡顿几秒甚至几十秒！
```

### 5.3 Redis 的渐进式 rehash

```
渐进式 rehash = 把一次大 rehash 拆成多次小操作：

第 1 步: 创建新表，但旧表保留
         ┌──────┐    ┌──────┐
         │ 旧表  │    │ 新表  │
         │ size  │    │ size  │
         │ = 4   │    │ = 8   │
         └──────┘    └──────┘

第 2 步: 每次处理命令时，顺便搬移旧表的一个 bucket
         GET key → 搬移 bucket[0]
         SET key → 搬移 bucket[1]
         INCR    → 搬移 bucket[2]

第 3 步: 所有 bucket 搬完 → 释放旧表
```

**渐进式 rehash 的效果**：

```
不阻塞 Redis — 每步只搬少量数据
时间均匀分摊 — 1000 万次 rehash 分摊到后续 1000 万个命令上
读写期间是安全的 — 查询时两个表都查，写时只写新表
```

## 6. 过期删除源码逻辑

### 6.1 两种删除策略

Redis 的过期 key 删除不是"到时间就立刻删除"，而是两种策略配合：

```
策略一：惰性删除（Lazy Deletion）

  当你 GET 一个 key 时，Redis 先检查它是否过期
  如果过期 → 删除它，返回 nil
  如果没过期 → 正常返回

  优点：CPU 友好（只删除被访问的过期 key）
  缺点：有些过期 key 可能永远不被访问 → 浪费内存


策略二：定期删除（Active Expiration / 定时扫描）

  Redis 每隔 100ms 执行一次以下操作：
    ① 从设置了过期时间的 key 中随机取 20 个
    ② 检查哪些过期了，删除
    ③ 如果过期比例 > 25%，重复步骤 ①~②
    ④ 但总耗时不超过 25ms

  优点：保证过期 key 最终会被清理
  缺点：浪费一部分 CPU


配合效果：
  ┌──────────────────────────────────┐
  │  大部分过期 key 由惰性删除处理     │
  │  懒删除没碰到的 → 定期删除兜底    │
  │  定期删除来不及的 → 内存不够时     │
  │     → Redis 用 maxmemory 策略淘汰  │
  └──────────────────────────────────┘
```

### 6.2 内存淘汰策略（maxmemory-policy）

当内存达到 `maxmemory` 限制时，Redis 用配置的策略淘汰 key：

| 策略 | 行为 |
|------|------|
| `noeviction` | 不淘汰，写入返回错误（默认） |
| `allkeys-lru` | 淘汰最近最少使用的 key |
| `allkeys-lfu` | 淘汰最不经常使用的 key（4.0+） |
| `volatile-lru` | 淘汰设置了过期时间的 key 中最近最少使用的 |
| `volatile-ttl` | 淘汰 TTL 最短的 key |
| `volatile-random` | 在设置了过期时间的 key 中随机淘汰 |

## 7. 大 Key 问题

### 7.1 什么是大 Key？

大 Key 没有一个严格的定义，但通常指：

| Key 类型 | "大"的标准 |
|----------|-----------|
| String | 值 > 10KB |
| List | 元素 > 10000 个 |
| Hash | 字段 > 1000 个 或 总大小 > 1MB |
| Set | 成员 > 5000 个 |
| ZSet | 成员 > 5000 个 |
| Stream | 消息 > 10000 条 |

### 7.2 大 Key 的三个问题

```
问题一：扫描阻塞

  KEYS *、SMEMBERS huge_set、LRANGE huge_list
  这些命令要遍历所有元素 → 单线程执行期间全部阻塞！

问题二：删除阻塞

  DEL huge_list（list 有 100 万个元素）
  → Redis 要释放 100 万个节点的内存
  → 这期间不能处理任何请求！
  → 高版本引入了 UNLINK 命令（后台异步删除）

问题三：网络阻塞

  GET huge_string（100MB 的 JSON）
  → 这个 100MB 要从 Redis 传输到客户端
  → 传输期间占用大量网络带宽
  → 其他请求等待
```

### 7.3 如何检测大 Key？

```
# 查看 key 近似大小
redis> MEMORY USAGE mykey
(integer) 1024000

# 查看 key 的底层信息
redis> DEBUG OBJECT mykey
Value at: 0x7f8c1c0068e0 refcount:1 encoding:raw serializedlength:10240 ...
```

> **更好的方式**：用 `redis-cli --bigkeys` 扫描整个 Redis，列出所有大 Key。生产环境建议在从节点或低峰期执行。

## 10. 自己动手

1. **RESP 协议实验**：写一个 Python 脚本，用 socket 连接 Redis，手动发送 `*3\r\n$3\r\nSET\r\n$3\r\nkey\r\n$5\r\nvalue\r\n`，看看能不能收到 `+OK\r\n`
2. **OBJECT ENCODING 观察**：创建不同类型的 key，用 `OBJECT ENCODING key` 看底层编码
3. **观察转换阈值**：往 Hash 里加字段，看什么时候从 ziplist 变成 hashtable
4. **模拟渐进式 rehash**：往一个 Set 里加大量元素，添加过程中不断执行其他命令，观察有没有阻塞
5. **大 Key 检测**：创建一个大的 List 或 Hash，用 `MEMORY USAGE` 和 `DEBUG OBJECT` 查看
6. **惰性删除验证**：设一个过期时间为 1 秒的 key，等 2 秒后 GET 它——看它还在不在
7. **maxmemory 实验**（选做）：给 Redis 设 maxmemory=10MB，然后不断写入数据，观察淘汰策略的行为
