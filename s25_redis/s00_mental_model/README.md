## 1. 没有 Redis 的痛苦

先回忆一下：你做一个网站，用户量从 100 人涨到了 10 万人。发生了什么？

```
最初（100 用户）：
  ┌──────────────┐    请求     ┌──────────────┐
  │  浏览器       │  ───────→  │  App 服务器   │  ───────→  │  MySQL 数据库 │
  │               │  ←───────  │              │  ←───────  │               │
  └──────────────┘  响应       └──────────────┘  查询       └──────────────┘
  App 请求什么数据，MySQL 就给什么 —— 一切正常。

后来（10 万用户）：
  ┌──────────────┐    请求     ┌──────────────┐
  │  浏览器 1     │  ───────→  │  App 服务器 1 │  ───────→  ┌──────────────┐
  │  浏览器 2     │  ───────→  │  App 服务器 2 │  ───────→  │  MySQL 数据库 │
  │  ...          │  ───────→  │  ...          │  ───────→  │  (瓶颈!!)     │
  │  浏览器 N     │  ───────→  │  App 服务器 N │  ───────→  └──────────────┘
                                                        每次请求都查数据库，
                                                        越来越慢，最终超时。
```

这个方案的致命问题：

| 问题 | 为什么痛苦 |
|------|-----------|
| **每次请求都要查数据库** | 用户看一个页面需要读 5 次 MySQL——用户信息、文章内容、评论数、点赞状态、通知。10 万人同时在线 = 50 万次 DB 查询/秒。 |
| **多台服务器之间没有共享状态** | 用户登录后 session 存在 App 服务器 A 的内存里，下次请求落到 App 服务器 B——「请重新登录」。 |
| **响应慢** | MySQL 的数据在硬盘上，一次查询最少 10ms。用户每等 100ms，转化率下降 7%。 |
| **实时功能需要额外基础设施** | 想做一个「用户 A 修改了文档，用户 B 实时看到更新」——没有 Redis 你需要搭建一套 WebSocket + 消息队列。 |
| **限流很难做** | 想限制「每个用户每秒最多 10 个请求」——每次请求都要查数据库计数，比不限制还慢。 |
| **缓存很麻烦** | 手动在代码里写 `if cache.has(key): return cache.get(key) else: db.query()` ——每个项目重复造轮子，缓存失效逻辑容易出 bug。 |

**高并发场景下 MySQL 扛不住，而多台服务器之间又需要一块公共的、极快的、共享的存储区域。** 这就是 Redis 要解决的问题。

## 2. Redis 的核心思想：内存即存储

你习惯的数据库（MySQL、PostgreSQL）的工作方式是：

```
MySQL 的世界观：
  硬盘 ────────────────────────────── 内存 ────── CPU
  │  数据文件 (.ibd / .frm)   │      │ Buffer  │  │ 查询  │
  │  所有数据最终存这里        │      │ Pool    │  │ 引擎  │
  │  断电后数据还在            │      │ 缓存热点 │  │ 计算  │
  └────────────────────────────┘      └─────────┘  └───────┘
  
  流程: 硬盘 → 读入内存 → CPU 处理 → 写回硬盘
  关键: 硬盘是最终存储地，内存是缓存。
```

**Redis 的世界观完全反过来：**

```
Redis 的世界观：
  内存 ────────────────────────────── 硬盘
  │  所有数据都在这里              │  │ 持久化备份  │
  │  String / List / Hash / Set   │  │ RDB 快照    │
  │  ZSet 全部在内存里            │  │ AOF 日志    │
  │  读写速度 ~100ns              │  │ 断电恢复用  │
  │  断电就丢了                   │  │ 不是主存储  │
  └───────────────────────────────┘  └─────────────┘
  
  流程: 内存读写 → 异步备份到硬盘
  关键: 内存是最终存储地，硬盘只是备份。
```

### 为什么内存这么快？

| 存储介质 | 延迟 | 对比 |
|---------|------|------|
| CPU 寄存器 | ~1 ns | — |
| 内存 (RAM) | ~100 ns | 1 倍 |
| SSD (NVMe) | ~100 μs | **慢 1000 倍** |
| 机械硬盘 | ~10 ms | **慢 100,000 倍** |
| 网络请求 (同机房) | ~500 μs | — |

> **内存比 SSD 快 1000 倍，比机械硬盘快 10 万倍。**
>
> 这就是 Redis 存在的理由——把数据放在内存里，读写速度瞬间完成。
> 而 MySQL 的大部分时间是花在「从硬盘读数据到内存」这个 IO 等待上。

### 不只是缓存

很多人以为 Redis 只是「缓存」——给 MySQL 挡一层查询。这是对的，但只对了一小部分。

Redis 能做的远比缓存多：
- **计数器**：网站实时访问量、点赞数（谁没事儿去 MySQL 里 +1？）
- **排行榜**：游戏积分榜、热门文章（用 SQL `ORDER BY score LIMIT 100` 在千万数据上跑？）
- **消息队列**：异步任务、秒杀请求排队（不用再装一套 RabbitMQ）
- **分布式锁**：多台服务器抢一个资源（避免「两个人同时下单最后一件商品」）
- **实时协同**：WebSocket 状态共享、在线用户列表
- **Session 存储**：多台 App 服务器共享用户登录状态

> **把 Redis 理解成「内存中的共享数据中枢」**，而不仅仅是「缓存」——这才是正确的姿势。

## 3. 共享黑板：Redis 的心智模型

现在，忘掉「数据库」「缓存」「K-V 存储」这些术语。让我们建立一个新的心智模型：

### 黑板

想象公司茶水间里有一块**大白板**。任何人路过都可以：
- 拿起马克笔**写**一行字（SET）
- **读**任意一行字（GET）
- **擦掉**一行字（DEL）
- 用**消失墨水**写字——30 秒后自动消失（EXPIRE）

```
┌─────────────────────────────────────────────────┐
│                      共 享 黑 板                  │
│                                                   │
│  ┌─────────────────────────────────────────────┐  │
│  │  user:1001 → "张三, VIP会员, 注册于2024"    │  │  ← String
│  │  user:1002 → "李四, 普通用户, 注册于2025"  │  │  ← String
│  │  recent:posts → [Redis教程, Python入门, ...] │  │  ← List
│  │  article:42:tags → {Redis, 教程, NoSQL}     │  │  ← Set
│  │  user:1001 → name:张三  age:28  city:北京   │  │  ← Hash
│  │  leaderboard → 张三:95  李四:88  王五:72    │  │  ← ZSet
│  │  code:1234 → "验证码" (⚠ 120秒后消失)       │  │  ← 消失墨水
│  └─────────────────────────────────────────────┘  │
│                                                   │
│  可读可写  |  实时  |  所有人可见                  │
│  断电就丢  |  但可以用照片/日志恢复                │
└─────────────────────────────────────────────────┘
```

### 核心概念 1：黑板上总是「最新的值」

每次你写同一个位置，旧值被覆盖。黑板不保留历史版本。

```
> SET user:1001 "老值"
> SET user:1001 "新值"    ← 覆盖，老值没了
> GET user:1001
"新值"                    ← 永远读到最新的
```

> 这就是 Redis 和 Git 最大的不同——Redis 没有版本历史，只有此时此刻的值。
> 但换来的是**极致的速度**。

### 核心概念 2：key = 黑板上的标题

黑板上的每一行都有一个**标题（key）**，通过标题找到内容。

```
无需翻页，无需索引，无需 SQL——
你知道标题，直接找到内容。

GET user:1001     → "张三"
GET article:42    → "Redis 教程"

不像 MySQL 那样要 SELECT * FROM users WHERE id = 1001，
Redis 是直接基于 key 的哈希表查找——O(1) 复杂度。
```

> **key 的命名就是你的「 schema 」**。
> Redis 没有表结构，所以你要通过 key 的命名来组织数据：
> - `user:1001` = 用户 1001
> - `article:42` = 文章 42
> - `order:20260701:8888` = 订单 8888
>
> 冒号作为分隔符，形成层级结构——这是 Redis 社区的通用约定。

### 核心概念 3：共享 = 所有人看到同一块黑板

这是 Redis 和「本地内存变量」的本质区别。

```
┌─────────────────────┐      ┌─────────────────────┐
│  App 服务器 1        │      │  App 服务器 2        │
│  ├─ 本地变量 A = 1   │      │  ├─ 本地变量 A = 2   │
│  └─ 读黑板: user=张三│      │  └─ 读黑板: user=张三│
│                       │      │                      │
│  各自有各自的本地变量  │      │  各自有各自的本地变量 │
│  → 但读黑板得到的     │      │  → 但读黑板得到的     │
│    永远是一样的       │      │    永远是一样的       │
└─────────────────────┘      └─────────────────────┘
                           │
                           │  SET / GET
                           ▼
                  ┌─────────────────────┐
                  │     共 享 黑 板      │
                  │                     │
                  │  user → "张三"      │
                  │                     │
                  │  所有服务器看到      │
                  │  同一份数据          │
                  └─────────────────────┘
```

> **本地变量 = 你自己的草稿本（别人看不到）**
> **Redis = 茶水间的公共黑板（所有人都能看到和修改）**

这就是为什么 Redis 能解决多服务器间的状态共享问题——session 存到 Redis 里，所有 App 服务器都能读到。

### 核心概念 4：单线程 = 不会有人同时改同一行

Redis 的核心是**单线程处理命令**——同一时刻只有一个命令在执行。

```
想象黑板前站着一个黑板管理员：
  ┌──────────────────────────────────┐
  │ 黑板管理员                      │
  │ 一次只处理一个请求              │
  │                                 │
  │ ① 用户 A: "帮我读 user:1001"    │
  │ ② 用户 B: "帮我写 user:1001=新值"│
  │ ③ 用户 C: "帮我读 user:1001"    │
  │                                 │
  │ 严格按照顺序，一个一个来。       │
  └──────────────────────────────────┘
```

这意味着：
- **不需要锁**——不会出现两个请求同时写导致数据错乱
- **原子性**——`INCR` 就是「读 → +1 → 写」，中间不会被插队
- **性能可预测**——没有上下文切换、没有锁竞争

> 对比 MySQL：100 个请求同时 `UPDATE users SET count = count + 1 WHERE id = 1` 需要行锁、事务、MVCC。
> Redis 的 `INCR count`：一个命令，不需要锁，因为只有一个管理员在处理。

### 核心概念 5：消失墨水 = 自动过期

你可以用**消失墨水**写字——设置一个过期时间，到期自动消失。

```
> SET code:1234 "验证码" EX 120    ← 用消失墨水写，120秒后消失

120 秒内:
  GET code:1234 → "验证码"

120 秒后:
  GET code:1234 → (nil)            ← 墨水已经消失，黑板上什么都没有了
```

Redis 的过期机制是它区别于传统数据库的核心特性：
- 验证码、会话 token、临时缓存——这些「有过期时间」的数据天然适合 Redis
- 你不用写定时任务去清理过期数据——Redis 自动帮你做

## 4. 五种数据类型：黑板上的五种组织方式

Redis 不只是「能存值」——它提供了**5 种数据结构**，每种解决一类特定问题。

这里只做**快速预览**，让你知道「有这几种工具」。s04~s07 会挨个深入。

### String（字符串）—— 一行文字

```
黑板上的一行：标题 + 一个值

"user:1001" → "张三, VIP会员, 注册于2024"
"code:1234" → "验证码"  ⚠ 120秒后消失

用途：缓存网页、存 JSON 片段、计数器、验证码
```

### List（列表）—— 有序清单

```
黑板上的一列条目，有顺序、可重复

"recent:posts" → ① "Redis教程"  ② "Python入门"  ③ "Git技巧"

用途：消息队列（LPUSH + BRPOP）、最新动态列表、时间线
```

### Hash（哈希）—— 带字段的表单

```
黑板上的一个区域，里面有多行字段，每行是一个字段名 + 值

"user:1001" →  name : "张三"
               age  : 28
               city : "北京"

用途：存对象（用户信息、文章、商品）、更新个别字段
```

### Set（集合）—— 一袋标签

```
黑板上的一个盒子，里面装着一堆不重复的小球

"article:42:tags" → { "Redis" "教程" "NoSQL" }

特性：无序、不重复、支持交/并/差运算
用途：标签系统、共同好友、去重
```

### ZSet（有序集合）—— 排行榜

```
黑板上的一份榜单，每位成员带一个分数，按分数排序

"leaderboard" →  张三: 95分  (第 1 名)
                 李四: 88分  (第 2 名)
                 王五: 72分  (第 3 名)

用途：积分排行榜、延迟队列、范围查询
```

### 快速对照

| 数据类型 | 黑板类比 | 适合场景 | 章节 |
|---------|---------|---------|------|
| **String** | 一行文字 | 缓存、计数器、验证码 | s01~s03 |
| **List** | 有序清单 | 消息队列、最新动态 | s04 |
| **Hash** | 带字段的表单 | 对象存储、配置项 | s05 |
| **Set** | 一袋不重复的小球 | 标签、去重、共同好友 | s06 |
| **ZSet** | 排行榜 | 积分榜、延迟队列 | s07 |

## 6. 一个操作的完整旅程

以「用户登录后，把用户信息缓存到 Redis」为例，用黑板模型理解整个过程：

### 场景：用户张三登录，App 需要缓存他的信息

```
Step 1: 浏览器 POST 登录请求
        → App 服务器验证用户名密码
        → 从 MySQL 查出用户信息（经过漫长等待 ⏳）
        → 决定把用户信息缓存到 Redis，下次不用再查数据库

Step 2: App 服务器执行:
        SET user:1001 '{"name":"张三","level":"VIP","points":500}' EX 3600

        → 在黑板上写下：
          标题: "user:1001"
          内容: '{"name":"张三","level":"VIP","points":500}'
          墨水: 消失墨水（3600 秒后自动擦除）

Step 3: 用户刷新页面（或另一个用户请求张三的信息）
        → App 服务器执行:
           EXISTS user:1001       ← 检查黑板上有这个标题吗？
           → 返回 1（有！不用查 MySQL 了！）
        → App 服务器执行:
           GET user:1001
        → 直接从黑板上读取（~100ns），返回给浏览器

        黑板上的值还在，不用去 MySQL——
        这一次请求省掉了一次数据库查询。

Step 4: 1 小时后（3600 秒后）
        → 消失墨水生效，黑板上 "user:1001" 的内容自动消失了
        → 下次请求时 GET user:1001 返回 (nil)
        → App 从 MySQL 重新读取，再次写入黑板（循环）
```

### 这个旅程告诉我们什么？

```
不用 Redis:
  每次请求 → 查 MySQL → 等 10ms → 返回数据 ← 每次都查

用 Redis:
  第一次请求 → 查 MySQL → 写入黑板 → 返回
  后续每次  → 直接读黑板 → 0.1ms → 返回  ← 快 100 倍

MySQL 本身也很快——但快不过内存。
Redis 的核心价值就是用内存速度解决"同一份数据被反复读取"的问题。
```

## 7. 进入实操之前

下一章（s01）你将在终端里执行真正的 Redis 命令。在此之前，回顾一下你的「地图」：

| 概念 | 一句话 |
|------|--------|
| Redis | 一块所有人共享的内存黑板 |
| SET | 在黑板上写一行字 |
| GET | 从黑板上读一行字 |
| DEL | 擦掉一行字 |
| EXPIRE / TTL | 消失墨水 / 查还有多少秒消失 |
| INCR | 黑板上画「正」字计数，没人会画乱 |
| String | 一行文字 |
| List | 有序清单（左边推入、右边弹出=消息队列） |
| Hash | 带字段的表单（像表格的一行） |
| Set | 不重复的集合（标签、去重、交集） |
| ZSet | 带分数的排行榜（按分数排序） |
| RDB | 给黑板拍一张照片，存到硬盘 |
| AOF | 每次写操作都记在本子上，断电后重做 |
| 单线程 | 黑板管理员一次只处理一个请求，不需要锁 |

> 如果你暂时没完全理解 ZSet 和 List 的区别、RDB 和 AOF 的区别——**完全没关系**。
>
> s00 的任务只是让你知道「有共享黑板这么一张地图存在」。
> 后面每一章会反复回到这张图，你会越来越清晰。
>
> 记住一件事就够了：**Redis 是一块共享黑板，所有操作都是在黑板上写字或读字。**

## 8. 自己动手（不敲命令，动脑即可）

1. **想象你的场景**：你正在做一个博客网站，有用户系统、文章系统、评论系统、标签系统。想想哪些数据适合放在 Redis 这块黑板上？哪些应该留在 MySQL 里？

2. **设想一个问题**：你的网站突然爆火，用户量翻了 100 倍。如果没有 Redis，MySQL 会怎样？用 Redis 缓存用户信息、文章内容之后，情况有什么不同？

3. **设计几个 key 命名**：如果需要把用户信息、文章详情、文章的标签分别缓存到 Redis，你会怎么给它们命名？试着用冒号分隔的层级结构设计 5 个 key。

4. **回忆一下**：不看上面的表，能用一句话说出 Redis 和 MySQL 的核心区别吗？能说出 String、List、Hash 三种数据类型在黑板上怎么体现吗？

5. **预览下一章**：确认你本地有 Redis 可用。在终端运行：
   ```
   redis-cli ping
   ```
