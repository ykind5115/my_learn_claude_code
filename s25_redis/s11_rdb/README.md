> *"SAVE 不是备份，是给整块黑板拍一张照片。BGSAVE 是让助手帮你拍。"*
>
> **前提知识**: 理解 s00 的黑板模型。知道 Redis 的数据存在内存里，断电就丢。

## 1. 为什么需要持久化？

Memory is volatile. 电源一断，内存里的数据全没了。

对比一下：

| 数据库类型 | 数据存储位置 | 断电后 |
|-----------|-------------|--------|
| MySQL / PostgreSQL | 硬盘 | 数据还在 |
| MongoDB | 硬盘 | 数据还在 |
| Redis | 内存 | **全部丢失** |

Redis 是内存数据库，内存本身是易失的。如果你在 Redis 里存了用户购物车、会话信息、计数器，断电后：

| 应用场景 | Redis 挂了 = |
|---------|-------------|
| 缓存 | MySQL 扛住（但瞬间压力暴增） |
| Session | 所有用户需要重新登录 |
| 购物车 | 用户丢失购物车内容 |
| 计数器 | 计数重置 |
| 消息队列 | 队列中的消息丢失 |

> **持久化就是把内存中的数据保存到硬盘**，这样即使 Redis 重启，数据还能恢复。

Redis 提供了两种持久化方式，这一章先讲第一个：

| 方式 | 黑板类比 | 特点 |
|------|---------|------|
| **RDB**（Redis Database） | 给整块黑板拍一张照片 | 定时全量快照，恢复快，但可能丢数据 |
| **AOF**（Append Only File） | 把每次写字动作记在本子上 | 记录细，丢数据少，但文件大、恢复慢 |

## 2. 在黑板模型下理解 RDB

RDB = Redis Database Backup File

### 类比

```
正常运行时（黑板状态）：
┌──────────────────────────────────────────┐
│  黑板上写满了数据                        │
│  user:1001 → "张三"                      │
│  product:42 → "iPhone 15"               │
│  cart:1001 → ["手机", "充电器", "耳机"] │
└──────────────────────────────────────────┘

拍 RDB 快照时（拍照）：
┌──────────────────────────────────────────┐
│  📸 咔嚓！给整个黑板拍一张照片            │
│     ↓                                    │
│  dump.rdb ✓  照片存在硬盘上              │

恢复时（根据照片还原）：
┌──────────────────────────────────────────┐
│  Redis 重启 → 读取 dump.rdb              │
│     ↓                                    │
│  黑板上的内容恢复成拍照时的样子           │
└──────────────────────────────────────────┘
```

### 关键理解

- **RDB 是定时全量快照**——它不是每写一笔都记录，而是每隔一段时间拍一张完整的照片
- **RDB 文件是压缩的二进制文件**——不是文本文件，不能直接用文本编辑器查看
- **RDB 只保存"拍照那一刻"的数据**——拍照之后写入的数据不在这张照片里
- **RDB 恢复速度极快**——因为是一个完整的、排好序的数据文件，直接加载到内存就行

## 3. SAVE vs BGSAVE — 自己拍 vs 让助手拍

### SAVE — 阻塞式快照

```bash
redis> SAVE
OK
```

- Redis 主进程**直接执行快照**
- 在快照完成之前，**阻塞所有其他命令**
- 如果数据量 10 GB，SAVE 期间整个 Redis 不可用

> **生产环境绝不用 SAVE。** 它就等于你放下所有工作亲自去拍照，其他事一概不处理。

### BGSAVE — 后台快照

```bash
redis> BGSAVE
Background saving started
```

- Redis 主进程**fork 出一个子进程**，子进程执行快照
- 主进程**继续处理请求**，不阻塞
- BGSAVE = "让助手帮你拍，你继续干活"

### 对比

| 特性 | SAVE | BGSAVE |
|------|------|--------|
| 阻塞？ | ✅ 阻塞所有命令 | ❌ 不阻塞（但 fork 瞬间可能卡顿） |
| 谁执行 | 主进程 | 子进程（fork） |
| 内存占用 | 无需额外内存 | fork 期间需要双倍内存（写时复制可优化） |
| 适用场景 | 停机维护、关机前 | 日常定时持久化 |
| 手动触发频率 | 几乎不用 | 按策略自动触发 |

### LASTSAVE — 最后一次快照的时间

```bash
redis> LASTSAVE
(integer) 1720522300   # Unix 时间戳
```

## 4. 写时复制（Copy-on-Write）

为什么 BGSAVE 不阻塞写入？核心就是操作系统的 **fork() + Copy-on-Write（写时复制）** 机制。

### 4.1 fork() 是什么？

fork() 是 Unix/Linux 系统调用，创建一个和当前进程几乎完全一样的子进程。

```
fork() 之前：
  ┌────────────────────────────────┐
  │  主进程（Redis Server）         │
  │  内存: 4 GB（全部 Redis 数据）  │
  └────────────────────────────────┘

fork() 之后：
  ┌────────────────────────────────┐
  │  主进程（Redis Server）         │
  │  内存: 4 GB                      │
  └────────────────────────────────┘
  ┌────────────────────────────────┐
  │  子进程（RDB 快照进程）         │
  │  内存: 和主进程共享             │
  └────────────────────────────────┘
```

fork 创建的子进程**共享父进程的内存页**——子进程看到的是 fork 那一刻的内存快照。

### 4.2 Copy-on-Write 机制

fork 时，父子进程共享同一份物理内存。只有**当某个进程要修改一页内存时**，操作系统才复制这一页给修改方。

```
写入发生时：

  主进程要修改 user:1001 的值：

  ┌────────────────────────────────┐
  │  主进程                          │
  │  ┌──────────┐  ┌──────────┐    │
  │  │ user:1001│  │ user:1002│    │  ← 修改 user:1001
  │  │ "张三"   │  │ "李四"   │    │     操作系统复制这一页
  │  └──────────┘  └──────────┘    │
  └────────────────────────────────┘
         │ 复制这一页
         ▼
  ┌────────────────────────────────┐
  │  子进程（RDB 快照进程）         │
  │  ┌──────────┐  ┌──────────┐    │
  │  │ user:1001│  │ user:1002│    │  ← 看到的是 fork 时的值
  │  │ "张三"   │  │ "李四"   │    │     （"旧"值）
  │  └──────────┘  └──────────┘    │
  └────────────────────────────────┘
```

### 4.3 为什么这很重要？

- **子进程看到的是 fork 那一时刻的数据快照**——一致性保证
- **主进程继续处理新的写入请求**——不阻塞
- **只有被修改的页面才需要复制**——节省内存
- 但如果写入量很大（大量页面被修改），内存开销可能接近双倍

> **关键**：BGSAVE 生成的 RDB 文件包含的是 fork 那一刻的数据，不是 BGSAVE 结束时。这意味着在 BGSAVE 过程中写入的新数据不会出现在这个 RDB 文件中。

### 4.4 fork 的代价

虽然 BGSAVE 不阻塞命令，但 fork() 本身不是免费的：

```bash
# 查看 fork 耗时
redis> INFO stats | grep fork
fork_usec:546           # fork 花了 546 微秒
```

- 数据量大时，fork 可能耗时几百毫秒
- fork 期间，所有请求都要等待（fork 本身是阻塞的）
- 如果 Redis 内存使用 20 GB，fork 的耗时可能达到秒级

## 5. RDB 配置策略

### 5.1 save 参数

```
save 900 1           # 900 秒（15 分钟）内至少有 1 个 key 变化 → BGSAVE
save 300 10          # 300 秒（5 分钟）内至少有 10 个 key 变化 → BGSAVE
save 60 10000        # 60 秒（1 分钟）内至少有 10000 个 key 变化 → BGSAVE
```

**格式**：`save <秒数> <变化次数>`

多个 save 配置是"或"的关系——满足任何一个就触发。

### 5.2 配置含义

```
时间轴：

第 0 秒: Redis 启动，数据为空
第 30 秒: 写入 5000 个 key  （save 60 10000 不满足——不到 60 秒）
第 45 秒: 又写入 5000 个 key  （共 10000 个，且在第 60 秒内吗？45 < 60，满足！）
         ↓
   BGSAVE 触发！拍一张快照

第 70 秒: 写入 1 个 key    （save 900 1 满足吗？900 > 70，不满足）
         秒数从上次快照后开始重新累计
```

### 5.3 手动查看配置

```bash
redis> CONFIG GET save
1) "save"
2) "900 1 300 10 60 10000"

redis> CONFIG GET dir
1) "dir"
2) "/var/lib/redis"           # RDB 文件保存目录

redis> CONFIG GET dbfilename
1) "dbfilename"
2) "dump.rdb"                 # RDB 文件名
```

### 5.4 关闭 RDB

```bash
# 方法 1：CONFIG SET（运行时）
redis> CONFIG SET save ""

# 方法 2：redis.conf（启动时）
save ""
```

> **关闭 RDB 的场景**：如果只用了 AOF 持久化，可以关闭 RDB 避免 fork 开销。但大多数场景建议保留 RDB 做备份。

### 5.5 其他相关配置

```bash
# RDB 文件压缩（默认 yes）
rdbcompression yes

# RDB 文件校验和（默认 yes）
rdbchecksum yes

# 如果 BGSAVE 出错，是否停止写入（默认 yes）
stop-writes-on-bgsave-error yes
```

## 6. RDB 的优缺点

### 优点

| 优点 | 说明 |
|------|------|
| **恢复极快** | RDB 是完整数据快照，加载到内存即可，比 AOF 快几个数量级 |
| **文件紧凑** | 压缩的二进制文件，体积小，适合备份传输 |
| **性能影响小** | BGSAVE 用子进程，主进程不受影响（fork 瞬间除外） |
| **适合灾难恢复** | 可以定时把 RDB 文件复制到远端，发生灾难时可以快速恢复 |

### 缺点

| 缺点 | 说明 |
|------|------|
| **可能丢数据** | 两次快照之间的数据全部丢失。如果 15 分钟拍一次，最多丢 15 分钟的数据 |
| **fork 耗时** | 数据量大时 fork 可能耗时几百毫秒到几秒，导致请求延迟尖刺 |
| **内存开销** | 写入量大时 Copy-on-Write 可能需要接近两倍内存 |
| **不实时** | 不是每笔写入都记录，不适合对数据完整性要求高的场景 |

## 7. 常见错误

### 错误 1：生产环境用 SAVE

```bash
# 危险！会阻塞所有请求
SAVE
```

生产环境永远用 BGSAVE。SAVE 只用在停机维护前做最后一次快照，或者确认没有请求时的关机操作。

### 错误 2：save 配置间隔太长

```bash
# 只配置了 900 秒 1 次
save 900 1
```

这意味着最多丢 15 分钟的数据。如果业务不能接受 15 分钟的数据丢失，要么缩短 RDB 间隔，要么改用 AOF。

### 错误 3：认为 BGSAVE 完全不消耗资源

BGSAVE 确实不阻塞命令，但：

- **fork 耗时**与数据量成正比（4 GB 数据约几百毫秒 fork 时间）
- fork 期间所有请求都会等待（fork 本身是阻塞的）
- **写入量大时内存可能翻倍**——Copy-on-Write 要复制被修改的内存页

### 错误 4：依赖 RDB 做主从复制的唯一方式

主从复制中，如果从节点连接主节点，主节点默认用 RDB 做全量同步。但如果 RDB 文件太大（几十 GB），全量同步的网络传输会严重影响主节点性能。

## 8. 你学到了什么

| 概念 | 一句话 |
|------|--------|
| **RDB** | 给 Redis 黑板拍一张完整的照片存到硬盘 |
| **SAVE** | 阻塞式快照（主进程亲自拍，拍完前不干活） |
| **BGSAVE** | 后台快照（fork 子进程拍，主进程继续干活） |
| **fork()** | 创建子进程，共享父进程内存快照 |
| **Copy-on-Write** | 修改时才复制内存页，不修改就共享 |
| **save 900 1** | 15 分钟内 ≥ 1 个 key 变化触发 BGSAVE |
| **LASTSAVE** | 查看最后一次成功快照的时间 |
| **RDB 优点** | 恢复极快、文件紧凑、性能影响小 |
| **RDB 缺点** | 可能丢数据、fork 耗时、内存开销 |

## 9. 自己动手

1. **查看当前 RDB 配置**：`redis-cli CONFIG GET save`，看你的 Redis 默认 save 策略是什么
2. **查看 RDB 文件位置**：`redis-cli CONFIG GET dir` 和 `redis-cli CONFIG GET dbfilename`
3. **手动触发 BGSAVE**：`redis-cli BGSAVE`，然后用 `redis-cli LASTSAVE` 确认时间
4. **查看 RDB 文件的修改时间**：在文件系统中找到 dump.rdb，看它的修改时间是否和 LASTSAVE 一致
5. **调整 save 配置**：`CONFIG SET save "5 1"`（5 秒内 1 个 key 变化就触发），然后 SET 一个 key，等 5 秒，检查文件修改时间
6. **查看 INFO persistence**：`redis-cli INFO persistence`，看 rdb_changes_since_last_save 和 rdb_last_bgsave_status 等字段
7. **运行 code.py**：`python s25_redis/s11_rdb/code.py`，看每一步的配置检查和命令执行
