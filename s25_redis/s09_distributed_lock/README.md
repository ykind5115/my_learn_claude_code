## 1. 为什么需要分布式锁？

**场景**：你的电商网站有三台服务器，同时处理用户的订单。用户点击"下单"按钮时：

```
三台服务器同时收到请求，操作同一个用户余额：

服务器 A: 读余额 (100元) → -50元 → 写回 (50元)
服务器 B: 读余额 (100元) → -30元 → 写回 (70元)   ← 错误！
服务器 C: 读余额 (100元) → -80元 → 写回 (20元)   ← 错误！

最终余额: 20元  (正确应该是 50-30-80 = -60? 等等，是 100-50-30-80 = -60)

不管怎么算，
三种不同的操作同时读到了"100 元"的旧值，各自计算，最后写回的结果覆盖了别人的结果。
```

> **问题本质**：多个服务器同时访问共享资源（用户余额、库存、文件），没有互斥机制。
>
> **解决方法**：让它们排队 — 拿锁的干活，没拿锁的等着。

### 为什么不能用传统的线程/进程锁？

```python
# ❌ 线程锁只在本进程内有效
import threading
lock = threading.Lock()   # 这个锁只对当前 Python 进程里的线程有效
# 服务器 B 和服务器 C 完全看不到这把锁！

# ✅ 需要一把「所有服务器都能看到」的锁
# → 放在共享黑板 (Redis) 上
```

> 分布式锁 = 一把存在于共享存储（Redis、ZooKeeper、etcd）中的锁，所有服务都能看到并遵守它的规则。

## 2. 在黑板模型下理解分布式锁

```
多个人的办公室里有一块黑板：

┌─────────────────────────────────────────────┐
│  共享黑板                                    │
│                                              │
│   2024-01-15 14:30:00                        │
│   lock:order:1001 = "服务器A已占用"          │
│                                              │
│  ┌──────────────┐                            │
│  │ 使用中！      │ ← 服务器 A 在黑板上写了    │
│  │ 服务器 A 在用 │   "使用中"，然后开始干活    │
│  └──────────────┘                            │
│                                              │
│  服务器 B 来了 → 看到"使用中"→ 等待           │
│  服务器 C 来了 → 看到"使用中"→ 等待           │
│                                              │
│  服务器 A 干完了 → 擦掉"使用中"               │
│  服务器 B 抢到 → 写上"服务器 B 已占用"       │
└─────────────────────────────────────────────┘
```

**核心规则**：
1. **先到先得** — 谁先写"使用中"谁拿到锁
2. **不能无限占用** — 必须设一个超时时间，防止拿锁的服务器挂了导致死锁
3. **用完必须释放** — 干完活了要擦掉"使用中"
4. **只能释放自己的锁** — 不能把别人写的"使用中"擦掉

## 3. 第一代：SETNX（简单但有问题）

Redis 提供了 `SETNX` 命令 — 如果 key 不存在就设置成功，存在则失败：

```python
# 服务器 A 尝试加锁
SETNX lock:order:1001 "server-a"    # → 1 (成功！锁归我了)
# ... 处理订单中 ...

# 服务器 B 尝试加锁
SETNX lock:order:1001 "server-b"    # → 0 (失败！锁已经被 A 拿了)
# ... 等待 ...

# 服务器 A 处理完了
DEL lock:order:1001                  # 释放锁
```

**问题：服务器 A 在加锁后、释放锁之前崩溃了！**

```python
SETNX lock:order:1001 "server-a"    # → 1 (成功)
# ... 服务器 A 突然宕机了 ...
# lock:order:1001 永远留在了 Redis 上
# 所有其他服务器永远无法获得这把锁！

# 这叫「死锁」— 锁永远不释放
```

> 这个问题的本质：**没有过期时间**。如果加锁后设置一个过期时间，即使服务器崩溃了，锁也会自动释放。

## 4. 第二代：SET NX PX（原子设置 + 过期时间）

```python
# 用一条命令完成：加锁 + 设置过期时间（原子操作）
SET lock:order:1001 "server-a" NX PX 30000

# 参数说明:
#   NX  = 只有 key 不存在时才设置 (同 SETNX)
#   PX  = 过期时间，单位毫秒 (这里 30000ms = 30s)
#   EX  = 过期时间，单位秒
```

> **为什么必须用一条命令？**
>
> 如果你分两条命令来做：
> ```python
> SETNX lock:order:1001 "server-a"     # 第 1 步：加锁
> EXPIRE lock:order:1001 30            # 第 2 步：设过期时间
> ```
> 如果第 1 步完成后、第 2 步开始前，服务器崩溃了 — 还是死锁！
>
> **SET NX PX 是原子操作**，要么都成功、要么都不成功，不存在中间状态。

## 5. 释放锁的坑 — 不能直接 DEL

### 问题：为什么不能直接 DEL？

```python
# 服务器 A 加锁，锁过期时间 30 秒
SET lock:order:1001 "server-a" NX PX 30000

# 服务器 A 的业务执行了 35 秒... (超过了锁的过期时间)
# 锁自动过期了

# 服务器 B 抢到了锁
SET lock:order:1001 "server-b" NX PX 30000    # 成功！

# 服务器 A 终于执行完了，然后... 
DEL lock:order:1001    # 把服务器 B 的锁释放了！ ← 灾难！
# 服务器 B 还在处理订单，锁却没了！
# 服务器 C 又拿到了锁，也来处理同一个订单...
```

> 直接 DEL 的问题：**可能删掉别人的锁**。

### 解决方案：用 Lua 脚本验证 value

加锁时写入一个**唯一标识**（如 UUID + 线程 ID），释放锁时检查 value 是不是自己的：

```lua
-- Lua 脚本：安全释放锁
-- KEYS[1] = 锁的 key
-- ARGV[1] = 唯一标识（加锁时写入的 value）

if redis.call("GET", KEYS[1]) == ARGV[1] then
    return redis.call("DEL", KEYS[1])
else
    return 0
end
```

```python
# Python 中使用 Lua 脚本释放锁
lock_value = uuid.uuid4().hex   # 唯一标识

# 加锁
redis.set(f"lock:order:{order_id}", lock_value, nx=True, px=30000)

# ... 执行业务 ...

# 释放锁（用 Lua 脚本确保安全和原子）
script = """
if redis.call("GET", KEYS[1]) == ARGV[1] then
    return redis.call("DEL", KEYS[1])
else
    return 0
end
"""
redis.eval(script, 1, f"lock:order:{order_id}", lock_value)
```

> **Lua 脚本保证了原子性**：判断 value 和删除 key 在同一步完成，不会被其他命令打断。

## 6. 看门狗（Watchdog）— 自动续期

### 问题

```python
SET lock:my_resource "server-a" NX PX 30000    # 30 秒超时

# 但如果业务逻辑需要 60 秒才能执行完...
# 30 秒后锁过期了 → 其他服务器抢到了锁
# 你的服务器还在处理 → 两个服务器同时操作同一个资源！
```

> 锁过期时间太短 → 业务没做完锁就没了
> 锁过期时间太长 → 服务器挂了要等很久才能释放锁
> **根本矛盾**：你无法预知业务需要多长时间。

### 解决方案：看门狗（自动续期）

```
加锁成功 → 启动一个后台线程（看门狗）

时间线:
  T+0s:   加锁成功 (TTL = 30s)
  T+10s:  看门狗检查 → 业务还在运行 → 续期 (TTL = 30s)
  T+20s:  看门狗检查 → 业务还在运行 → 续期 (TTL = 30s)
  T+30s:  业务完成 → 关机门狗 → 释放锁

如果服务器在 T+15s 挂了:
  T+30s:  看门狗线程也跟着挂了，不再续期
  T+45s:  锁过期 → 自动释放 → 其他服务器可以获取
```

**看门狗的逻辑**：
```
while 锁还存在 and 业务还在运行:
    EXPIRE lock_key 30    # 续期到 30 秒
    sleep(10)             # 每 10 秒检查一次
```

> **Redisson**（Java Redis 客户端）内置了看门狗机制。Python 中可以用 `redis-py` + 后台线程实现。

## 7. Redlock 算法简介（多节点场景）

### 问题

到目前为止，我们的锁都依赖于**单个 Redis 节点**：

```
单点故障问题：
  你从 Redis 主节点拿到了锁
  主节点还没有把锁同步到从节点，主节点挂了
  从节点变成了主节点 → 它不知道有这把锁
  另一个服务器从新主节点拿到了同一把锁 → 锁失效了！
```

### Redlock 的思路

Redlock 是 Redis 作者提出的分布式锁算法，用于**多 Redis 节点（一般是 5 个独立节点）**的场景：

```
1. 获取当前时间 T1
2. 依次向 N 个（通常是 5 个）Redis 节点请求加锁
3. 计算加锁耗时：elapsed = T2 - T1
4. 判断是否成功加锁：
   - 成功加锁的节点数 > N/2（超过半数）
   - 总耗时 < 锁的过期时间
5. 如果满足条件 → 锁有效；否则 → 释放所有节点上的锁
```

> **Redlock 不是银弹**。学术界对 Redlock 有争议（Martin Kleppmann 和 Redis 作者的著名辩论），核心分歧在于时钟假设。对于大多数应用场景，单 Redis 主节点的锁（加上合理的 fallback 策略）已经足够了。

## 8. 常见错误（新手必读）

### ❌ 错误 1：锁过期了任务还没做完

```python
# 锁设了 10 秒过期，但业务逻辑可能要 60 秒
redis.set("lock:pay:1001", "ok", nx=True, ex=10)
process_payment()    # 可能要 60 秒... → 锁过期了！
```

> **解决**：加看门狗续期，或估算好最大执行时间。

### ❌ 错误 2：忘记释放锁

```python
def do_something():
    redis.set("lock:resource", value, nx=True, ex=30)
    # ... 处理业务 ...
    if some_error:
        return   # ❌ 忘记释放锁！
    redis.delete("lock:resource")   # 正常情况释放了
```

> **解决**：用 try/finally 确保释放锁：
> ```python
> try:
>     redis.set("lock:resource", value, nx=True, ex=30)
>     # ... 业务逻辑 ...
> finally:
>     safe_release_lock(redis, "lock:resource", value)
> ```

### ❌ 错误 3：所有的服务器用同一个 value 加锁

```python
# 所有服务器都用 "locked" 作为 value
redis.set("lock:resource", "locked", nx=True, ex=30)
```

> 这样无法区分是谁的锁 → 释放锁时可能误删别人的锁。
> **每个服务器必须生成唯一的锁标识**（UUID 等）。

### ❌ 错误 4：SETNX 和 EXPIRE 分开写

```python
redis.setnx("lock:resource", value)   # 第 1 步
# ... 服务器在此时崩溃了 ...
redis.expire("lock:resource", 30)      # 第 2 步没执行 → 死锁！
```

> **必须用 SET NX PX 一条命令完成。**
