## 1. 为什么需要缓存？

数据库（MySQL、PostgreSQL）是可靠的，但也是**慢的**：

```
读一个用户信息:
  ┌─────────────────────────────────────────┐
  │  MySQL: 查磁盘 → 解析 SQL → 执行查询    │
  │          → 读取 B+ 树 → 返回结果         │
  │          耗时: 10 ~ 100ms                │
  └─────────────────────────────────────────┘

如果同一个用户信息被请求了 10000 次:
  每次都要走 MySQL → 10000 × 50ms = 500 秒！

用 Redis 缓存:
  ┌─────────────────────────────────────────┐
  │  第一次: 查 MySQL → 写入 Redis          │
  │  之后 9999 次: 直接查 Redis (1ms)       │
  │  总耗时: 50ms + 9999 × 1ms ≈ 10 秒     │
  └─────────────────────────────────────────┘

提速 50 倍！
```

**缓存的核心思想**：把热数据（频繁访问的数据）放在更快的小存储中，减少对慢存储的访问。

## 2. 在黑板模型下理解缓存

回到我们的共享黑板模型：

```
你的办公室里有两块记录工具:

┌─────────────────────────────────────┐
│  📋 黑板 (Redis)                    │
│  写在上面 → 随时可以擦掉             │
│  适合: 临时记录、快速查阅             │
│  问题: 断了电就没了                   │
│  容量: 有限 (内存)                   │
└─────────────────────────────────────┘

┌─────────────────────────────────────┐
│  🗄️ 档案室 (MySQL/PostgreSQL)       │
│  存在里面 → 永久保存                 │
│  适合: 最终凭证、完整记录             │
│  优点: 断电也不丢数据                 │
│  问题: 查起来慢 (磁盘 I/O)            │
└─────────────────────────────────────┘

正常流程：
  1. 去档案室查数据 → 抄到黑板上（方便下次看）
  2. 别人再问同样的问题 → 先看黑板，黑板上没有再去档案室
  3. 黑板上的字过一段时间擦掉（过期）→ 保证下次看到的是最新数据
```

> **缓存不是数据库的替代品，而是数据库的「加速层」**。数据只在黑板上？断电就丢了！数据一定要在档案室里有备份。

## 3. 最常用模式：Cache-Aside（旁路缓存）

这是最常用、最简单的缓存模式。它的流程只有 4 步：

```
要查用户信息 user:1001:

                                            ┌─────────┐
    ① 查缓存 ─────────────────────────────→ │  Redis   │
                                            └─────────┘
                                                  │
                 ┌─ 命中 (cache hit) ─────────────┤
                 │                                │
                 │ 直接返回 ←─────────────── 返回数据
                 │
                 └─ 未命中 (cache miss) ──────────┤
                                                  │
    ② 查数据库 ─────────────────────────────→  ┌────────┐
                                                │ MySQL  │
    ③ 写缓存 ←──── 返回结果 ──────────────── │        │
                                                └────────┘
    ④ 返回给用户
```

**Key 的设计规范**：
- 一般是 `业务:对象:ID` 格式，如 `user:1001`、`article:42`
- 值可以是 JSON 字符串，也可以是 Hash 结构

**什么时候写缓存？**
- **读取时**：Cache miss 后，从 DB 查到数据，写入缓存
- **更新时**：先更新 DB，再**删除**缓存（而不是更新缓存）

> ❓ 为什么更新时是"删除缓存"而不是"更新缓存"？
> 因为并发场景下，更新缓存容易导致数据不一致（后面会讲）。

## 4. 缓存穿透 — 查不存在的 key

### 问题描述

```python
# 攻击者不断请求不存在的用户
GET user:9999999      # 缓存没有
GET user:9999998      # 缓存没有
GET user:9999997      # 缓存没有
# 每次都穿透缓存 → 直接打到数据库 → 数据库压力暴增！
```

> **缓存穿透 = 查询一个缓存和数据库都不存在的数据**。每次请求都穿过了缓存，直接打在数据库上。如果被人恶意利用，数据库可能被打挂。

### 解决方案 1：空值缓存

```python
def get_user(user_id):
    data = redis.get(f"user:{user_id}")
    if data is not None:
        if data == "NULL":           # 之前查过，不存在
            return None
        return json.loads(data)

    data = db.query("SELECT * FROM users WHERE id = ?", user_id)
    if data is None:
        redis.set(f"user:{user_id}", "NULL", ex=60)   # 空值也缓存，但过期时间短
        return None

    redis.set(f"user:{user_id}", json.dumps(data), ex=3600)
    return data
```

### 解决方案 2：布隆过滤器（Bloom Filter）

**布隆过滤器**是一种空间效率极高的概率型数据结构。它可以非常确定地告诉你**「这个 key 一定不存在」**，但只能说**「可能存在」**（有误判率）。

```
┌──────────────────────────────────────────────────┐
│  布隆过滤器原理（以手机号黑名单为例）              │
│                                                    │
│  有一亿个手机号，不可能全加载到内存：              │
│    - HashSet 需要约 4GB 内存                       │
│    - 布隆过滤器只需要约 200MB                      │
│                                                    │
│  布隆过滤器的工作方式：                            │
│    ① 对每个手机号用 k 个哈希函数计算位置           │
│    ② 把位数组中对应位置标记为 1                   │
│    ③ 查询时，如果任何一个位置是 0 → 一定不存在     │
│                                                    │
│  「一定不存在」vs「可能存在」：                     │
│    - 不在黑名单的手机号 → 布隆过滤器能 100% 确定    │
│    - 在黑名单的手机号 → 有极小概率误判（调参控制）  │
└──────────────────────────────────────────────────┘
```

> Redis 4.0+ 提供了 `BF.ADD`、`BF.EXISTS` 等布隆过滤器命令（通过 RedisBloom 模块）。但理解原理比背命令更重要。

## 5. 缓存击穿 — 热点 key 过期

### 问题描述

```python
# 某个 key 是"热点 key"（比如首页推荐列表），每秒被访问 10000 次
# 突然，这个 key 过期了...

第 1 个请求: 缓存 miss → 查 DB → 耗时 200ms → 写缓存
第 2 个请求: 缓存 miss → 查 DB → 耗时 200ms → 写缓存
第 3 个请求: 缓存 miss → 查 DB → 耗时 200ms → 写缓存
# ... 同时 10000 个请求全部打到了 DB！
```

> **缓存击穿 = 一个热点 key 过期时，大量并发请求同时打到数据库。**

### 解决方案：互斥锁（Mutex）

```python
def get_hot_data():
    data = redis.get("hot:data")
    if data is not None:
        return data

    # 尝试获取锁，只有一个人能拿到
    lock_key = "lock:hot:data"
    if redis.setnx(lock_key, "1", ex=5):   # SETNX + 过期
        data = db.query("SELECT * FROM hot_items")
        redis.set("hot:data", json.dumps(data), ex=60)
        redis.delete(lock_key)              # 释放锁
        return data
    else:
        # 没拿到锁的人等一会儿再试
        time.sleep(0.1)
        return get_hot_data()               # 递归重试
```

> 这种方案虽然能保护数据库，但会降低并发时的响应速度。对于不要求强一致性的场景，更简单的方案是：**不给热点 key 设过期时间**，由后台任务异步更新。

## 6. 缓存雪崩 — 大量 key 同时过期

### 问题描述

```python
# 假设你给一批缓存设置了相同的过期时间：
redis.set("product:1001", data1, ex=3600)
redis.set("product:1002", data2, ex=3600)
redis.set("product:1003", data3, ex=3600)
# ... 10000 个商品全部设了 3600 秒过期

# 一小时后 → 所有 key 同时过期 → 所有请求同时打向数据库！
```

> **缓存雪崩 = 大量 key 在同一时间过期，导致数据库压力瞬间暴增。**

### 解决方案 1：随机过期时间

```python
import random

# 在基础过期时间上加上随机偏移量
base_ttl = 3600
random_ttl = base_ttl + random.randint(0, 600)    # 3600 ~ 4200 秒
redis.set(f"product:{id}", data, ex=random_ttl)
```

### 解决方案 2：多级缓存

```
请求到达 → 本地缓存 (内存) → Redis 缓存 → 数据库
             1ms           2~5ms       10~100ms

本地缓存（如 Python 的 functools.lru_cache 或 Guava Cache）：
  - 在应用服务器的内存中再缓存一层
  - 即使 Redis 挂了，还有本地缓存顶一下
  - 本地缓存过期时间比 Redis 短
```

### 解决方案 3：缓存预热 + 错峰更新

```python
# 上线前预先加载热点数据到缓存（不是等用户请求才加载）
def preheat_cache():
    hot_ids = [1001, 1002, 1003, ...]         # 预判热点
    for id in hot_ids:
        data = db.query(f"SELECT * FROM products WHERE id = {id}")
        ttl = 3600 + random.randint(0, 600)   # 随机 TTL
        redis.set(f"product:{id}", json.dumps(data), ex=ttl)
```

## 7. 常见错误（新手必读）

### ❌ 错误 1：更新数据库后更新缓存（而不是删除缓存）

```python
# ❌ 错误做法
def update_user(user_id, name):
    db.execute("UPDATE users SET name = ? WHERE id = ?", name, user_id)
    redis.set(f"user:{user_id}", json.dumps({"name": name}))   # 直接更新缓存

# ✅ 正确做法
def update_user(user_id, name):
    db.execute("UPDATE users SET name = ? WHERE id = ?", name, user_id)
    redis.delete(f"user:{user_id}")   # 删除缓存，下次读时重建
```

**为什么删除比更新安全？**

```
场景：两个并发请求同时操作同一个用户

请求 A：把 name 改成 "张三"    请求 B：把 age 改成 20

时间线：
  A 更新 DB (name = "张三")
  B 更新 DB (age = 20)
  B 更新缓存 (name: "李四", age: 20)   ← 缓存中的 name 变成了旧值"李四"
  A 更新缓存 (name: "张三", age: 18)   ← 缓存中的 age 变成了旧值 18

结果：DB 中是 (name: "张三", age: 20)，缓存中是 (name: "张三", age: 18) — 不一致！

如果用的是"删除缓存"策略：
  A 更新 DB (name = "张三")
  B 更新 DB (age = 20)
  B 删除缓存
  A 删除缓存
  下一次读 → cache miss → 从 DB 重建缓存 → 数据一致！
```

### ❌ 错误 2：忘记设置过期时间

```python
redis.set("user:1001", json.dumps(data))    # 没有 ex 参数！
```

**后果**：这个 key 永远不会过期。如果用户 1001 改了名字，缓存中还是旧数据。下次读到缓存命中，直接返回旧数据。

### ❌ 错误 3：缓存预热忘记做

新功能上线后，用户第一次访问时全部 cache miss → 所有请求同时打数据库。对于热点数据，一定要在发布前加载到缓存。

## 8. 你学到了什么

| 概念 | 一句话 |
|------|--------|
| 缓存 | 把慢存储的热数据复制到快存储中，加速读取 |
| Cache-Aside | 最通用模式：先查缓存 → miss 则查 DB → 写入缓存 |
| 缓存穿透 | 查不存在的数据 → 布隆过滤器 / 空值缓存 |
| 缓存击穿 | 热点 key 过期 → 互斥锁保护 |
| 缓存雪崩 | 大量 key 同时过期 → 随机 TTL / 多级缓存 |
| 更新策略 | 先更新 DB，再删除缓存（不是更新缓存） |
