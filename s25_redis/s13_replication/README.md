# s13: 主从复制 — 多块黑板同步

[s12](../s12_aof/) → `s13` → [s14](../s14_sentinel/)
> *"主黑板写了什么，副黑板跟着抄一遍。写走主，读走从。"*
>
> **前提知识**: 理解 RDB（s11）和 AOF（s12）持久化。

---

## 1. 为什么需要主从复制？

黑板上写了一堆重要数据。突然——

- **黑板坏了**（Redis 进程挂了）
- **黑板碎了**（服务器宕机）
- **维护时间**（要重启升级）

如果只有一块黑板，上面所有数据都丢了。

**主从复制 = 多块黑板实时同步。** 一块主黑板（Master）负责写，多块从黑板（Replica）负责同步并提供读服务。

```
写操作 → ┌──────────┐    同步    ┌──────────┐
         │ 主黑板    │ ────────→ │ 从黑板 1  │ ← 读操作
         │ (Master)  │           ├──────────┤
         └──────────┘           │ 从黑板 2  │ ← 读操作
                 │              ├──────────┤
                 │              │ 从黑板 3  │ ← 读操作
                 └─────────────→ └──────────┘
```

### 主从复制解决了什么问题？

| 问题 | 主从的解决方案 |
|------|--------------|
| 单点故障 | 主挂了，从节点还有数据 |
| 读压力大 | 多个从节点分担读请求 |
| 数据备份 | 从节点可用来做数据备份，不影响主节点 |
| 异地容灾 | 从节点可以部署在不同的机房/城市 |

## 2. 在黑板模型下理解主从

### 核心原则

- 只有**主黑板**能写——所有写入操作都在主节点执行
- **从黑板**只读——客户端从从节点读数据（默认配置）
- 主黑板会把自己写的每一行字实时同步给所有从黑板
- 如果某块从黑板断了，重连后会自动补上缺失的部分

### 一个比喻

```
主黑板的教室:

  老师（主）在黑板上写板书
  同学们（从）跟着抄笔记

  新同学迟到了（断线重连）
    没关系，看老师的完整笔记补上刚才漏掉的内容

  要查资料？
    翻自己笔记就行，不用去打扰老师
    这样老师可以专心写板书，不会被频繁打断
```

### 关键理解

```python
# 主从复制不是「主推数据给从」，而是「从主动找主要」。
# 从节点启动时或执行 REPLICAOF 命令后，主动连接主节点，
# 请求同步数据。
```

## 3. 配置主从关系

### 3.1 通过配置文件

在从节点的 `redis.conf` 中：

```redis
# 告诉从节点：谁是主节点
replicaof 192.168.1.10 6379

# 从节点是否只读（默认 yes）
replica-read-only yes
```

### 3.2 通过命令行

```bash
# 在从节点上执行（运行时生效，重启后丢失）
REPLICAOF 192.168.1.10 6379

# 取消复制（变回独立节点）
REPLICAOF NO ONE
```

### 3.3 查看复制状态

在主节点上查看：

```bash
redis-cli INFO REPLICATION
```

输出示例：

```
# Replication
role:master
connected_slaves:2
slave0:ip=192.168.1.11,port=6379,state=online,offset=12345
slave1:ip=192.168.1.12,port=6379,state=online,offset=12345
master_replid:abc123def456...
master_replid2:000000000000...
master_repl_offset:12345
second_repl_offset:-1
repl_backlog_active:1
repl_backlog_size:1048576
repl_backlog_first_byte_offset:1
repl_backlog_histlen:12345
```

在从节点上查看：

```bash
redis-cli INFO REPLICATION
```

```
# Replication
role:slave
master_host:192.168.1.10
master_port:6379
master_link_status:up
master_last_io_seconds_ago:0
master_sync_in_progress:0

```

### 关键字段说明

| 字段 | 含义 |
|------|------|
| `role` | 当前节点角色：master 或 slave |
| `connected_slaves` | 连接了几个从节点 |
| `slaveN` | 每个从节点的 IP、端口、状态、偏移量 |
| `master_link_status` | 主连接状态 up/down |
| `master_repl_offset` | 主节点的当前写入偏移量 |
| `slave_repl_offset` | 从节点的当前同步偏移量 |
| `repl_backlog_histlen` | backlog 中当前存储的数据量 |

## 4. 全量同步过程

### 什么时候发生？

- **第一次**建立主从关系
- 从节点断开重连，但**差异太大**（backlog 不够）
- 从节点的数据完全丢失（如新启动的实例）

### 六步走

```
┌─────────────────────────────────────────────────────────┐
│                       全量同步                            │
├─────────────────────────────────────────────────────────┤
│                                                         │
│  从节点                  主节点                           │
│    │                       │                            │
│    │  1. 连接 / REPLICAOF  │                            │
│    │──────────────────────→│                            │
│    │                       │                            │
│    │  2. PSYNC ? -1        │  ← "-1" 表示我没有任何数据   │
│    │──────────────────────→│                            │
│    │                       │                            │
│    │                       │  3. BGSAVE → RDB            │
│    │                       │     同时开始存 buffer        │
│    │                       │                            │
│    │  4. RDB 文件          │                            │
│    │←──────────────────────│                            │
│    │                       │                            │
│    │  5. 清空 + 载入 RDB   │                            │
│    │                       │                            │
│    │  6. buffer 增量命令   │                            │
│    │←──────────────────────│                            │
│    │                       │                            │
│    ▼                       ▼                            │
│  数据一致！               继续服务                        │
│                                                         │
└─────────────────────────────────────────────────────────┘
```

### replication buffer 是什么？

主节点在做全量同步时，不会停止服务。新的写入会：

1. 正常写入内存
2. 同时写入 **replication buffer**（一个内存缓冲区）
3. RDB 传完后，把 buffer 里的增量命令也发给从节点

这样从节点就能**赶上**主节点在同步期间产生的新数据。

### 全量同步的代价

| 代价 | 说明 |
|------|------|
| CPU | 主节点执行 BGSAVE，fork 子进程 |
| 内存 | fork 期间写时复制可能内存翻倍 |
| 网络 | 传输整个 RDB 文件（数据量大时可能几百 MB ~ GB） |
| 阻塞 | 从节点载入 RDB 时无法提供服务 |

> **所以：不要让从节点频繁断连。每次重连的全量同步都是有成本的。**

## 5. 增量同步

### 什么时候发生？

从节点**短暂断开后重连**，且它的偏移量还在主节点的 backlog 范围内。

### PSYNC2 协议

从 Redis 2.8 开始使用 `PSYNC`，Redis 4.0 升级为 `PSYNC2`。

```redis
PSYNC <replid> <offset>
```

- `replid`：主节点的复制 ID（每个主节点有一个唯一 ID）
- `offset`：从节点已经接收到的数据偏移量

> 翻译过来：**「我已经有这些数据了，从 offset 之后的说起」**

### 增量同步流程

```
从节点断开后重连
      │
      ▼
PSYNC <replid> <offset>    ← 告诉主节点我的位置
      │
      ▼
主节点检查 offset 是否在 backlog 范围内
      │
      ├── 在范围内 → CONTINUE + 发送差异数据
      │
      └── 不在范围内 → FULLRESYNC + 触发全量同步
```

### replication backlog — 环形缓冲区

主节点维护一个**环形缓冲区**，默认大小 1MB。

```
写方向 ◀─── ◀─── ◀─── ◀───
    ┌───┬───┬───┬───┬───┬───┬───┬───┐
    │ A │ B │ C │ D │ E │ F │ G │   │
    └───┴───┴───┴───┴───┴───┴───┴───┘
    ▲           ▲               ▲
    │           │               └── 主节点当前位置 (offset=7)
    │           └── 从节点曾在此 (offset=4)
    └── 最早可追到的位置 (offset=1)
```

关键配置：

```redis
# backlog 大小（默认 1MB）
repl-backlog-size 1mb

# backlog 过期时间（秒，0 = 永远不过期）
repl-backlog-ttl 3600
```

> **如何决定 backlog 大小？**  
> 按「主节点峰值写入速度 × 可接受的最大断连时间」估算。  
> 比如每秒 10KB 写入，允许断连 5 分钟 → 10KB × 300s = 3MB。

## 6. 读写分离

### 应用层如何实现

```
客户端（应用层）
      │
      ├── 写操作 ──────→ 主节点 (192.168.1.10:6379)
      │                     SET / DEL / INCR / ...
      │
      └── 读操作 ──────→ 从节点 (192.168.1.11:6379)
                     └── 从节点 (192.168.1.12:6379)
                           GET / EXISTS / LRANGE / ...
```

### Python 代码示意

```python
from redis import Redis

# 写操作 → 走主节点
master = Redis(host='master-ip', port=6379)
master.set('user:profile:1001', '{"name":"小明"}')

# 读操作 → 走从节点
replica = Redis(host='replica-ip', port=6379)
profile = replica.get('user:profile:1001')
```

### 读写分离的陷阱

**主从延迟**：写入主节点后立即读从节点，可能读到旧数据。

```
时间线:
  T1: 客户端 A 写入主节点  SET stock:100  "已售罄"
  T2: 客户端 B 读从节点    GET stock:100  → "有货"（还没同步）
  T3: 主→从 同步完成
```

解决方案：
- **对一致性要求高的操作**：强制走主节点读
- **使用 WAIT 命令**：等待至少 N 个从节点确认

```redis
SET stock:100 "已售罄"
WAIT 1 5000    ← 等待至少 1 个从节点确认，超时 5 秒
```

> **WAIT 是尽量保证，不是绝对保证。** 网络分区等极端情况仍可能丢失。

## 7. 常见错误

### ❌ 错误 1：从节点上有过期键

从节点自己不处理过期键——它依赖主节点发 DEL 命令。

```
主节点: SET session:abc "data" EX 10
       （10 秒后自动删除）
主节点: DEL session:abc    ← 主节点删除后，发 DEL 给从节点
从节点: 收到 DEL，删掉 key
```

**问题**：如果主节点到时间没来得及发 DEL（比如主节点很忙），从节点上还能读到这个本该过期的键。

### ❌ 错误 2：主从延迟导致读到旧数据

在读写分离架构中，写后立即读可能读到旧值。

> **对策**：业务层面区分「强一致」和「最终一致」操作。强一致走主，最终一致走从。

### ❌ 错误 3：主节点挂了，没人自动切

主从复制只是**数据冗余**，不是**故障转移方案**。

```bash
# 主节点挂了之后，需要人工操作：
# 选一个从节点，升它为主
REPLICAOF NO ONE    ← 断开复制，变为独立主节点

# 其他从节点指向新的主
REPLICAOF new-master-ip 6379

# 整个过程需要人介入 → 这段时间服务不可用
```

> **这就是下一章（s14 — Sentinel）要解决的问题：让这个过程自动化。**

### ❌ 错误 4：一台从节点连多台主节点

一个从节点只能有一个主节点。不能同时复制多个主节点。

```redis
REPLICAOF 192.168.1.10 6379
REPLICAOF 192.168.1.20 6379    ← 覆盖了上一个配置
```

### ❌ 错误 5：从节点可写（危险配置）

默认从节点是只读的（`replica-read-only yes`）。如果设置为 `no`：

```redis
replica-read-only no    ← 危险！
```

从节点上的写入**不会同步到主节点**，也不会同步给其他从节点。这会导致主从数据不一致——而且 Redis 不会告诉你。

## 8. 你学到了什么

| 概念 | 一句话 |
|------|--------|
| 主从复制 | 一块主黑板实时同步到多块从黑板 |
| 全量同步 | 从节点连上后，先传完整 RDB，再追增量 |
| 增量同步 | 从节点短暂断开后，只同步缺失的部分 |
| PSYNC2 | 从节点告诉主节点「我有的数据」，主节点只发缺少的 |
| replication buffer | 全量同步期间暂存的增量命令 |
| replication backlog | 主节点上的环形缓冲区，用于增量同步 |
| 读写分离 | 写走主、读走从，分散读压力 |
| 主从延迟 | 写入主 → 同步到从 有时间差 |

## 9. 自己动手

1. **启动两个 Redis 实例**：一个在 6379（主），一个在 6380（从），在从节点执行 `REPLICAOF 127.0.0.1 6379` 配置主从关系
2. **在主节点写入** `SET greet "hello"`，在从节点用 `GET greet` 确认同步
3. **在主节点和从节点上分别运行** `INFO REPLICATION`，观察字段差异
4. **停掉从节点**，在主节点写入新数据，重启从节点看它能否自动同步
5. **尝试在从节点上执行写入**（`SET test "x"`）——观察报错
6. **查看 backlog 大小**：`CONFIG GET repl-backlog-size`，理解默认值 1MB 是否适合你的场景
