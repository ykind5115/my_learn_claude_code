## 1. 为什么需要 Cluster？

前面两章解决的是「高可用」问题——数据有备份，主节点挂了能自动切。

但还有一个问题没解决：**单机容量上限**。

```
一台 Redis 服务器的内存是有限的：
  如果一台机器只有 64GB 内存
  而你的数据有 500GB

  主从复制？数据还是存在同一台机器上
  Sentinel？也只是多副本，总量没变

  你需要的是——把数据分到多台机器上存。
```

**Redis Cluster = 自动分片 + 高可用。**

```
                 客户端
                  │
    ┌─────────────┼─────────────┐
    ▼             ▼             ▼
┌──────────┐ ┌──────────┐ ┌──────────┐
│ 节点 1    │ │ 节点 2    │ │ 节点 3    │
│ 槽 0~5460 │ │ 槽 5461~ │ │ 槽 10923~│
│           │ │ 10922    │ │ 16383    │
│ 主 + 从   │ │ 主 + 从   │ │ 主 + 从   │
└──────────┘ └──────────┘ └──────────┘
```

## 2. 在黑板模型下理解 Cluster

### 16384 个槽位

```
想象一块超级大的黑板，大到一个人写不下。

我们把它切成 16384 块小拼图（槽位 / slots），
分给 3 块子黑板（节点）去写：

  子黑板 1:  负责槽 0 ~ 5460    （约 1/3）
  子黑板 2:  负责槽 5461 ~ 10922（约 1/3）
  子黑板 3:  负责槽 10923 ~ 16383（约 1/3）

每条数据（key）通过一个公式算出属于哪个槽：
  HASH_SLOT = CRC16(key) % 16384

然后去负责这个槽的节点上读写。
```

### 数据怎么找到正确的节点？

```
客户端 GET user:1001

  1. 计算 CRC16("user:1001") % 16384 → 假设结果是 7234
  2. 查本地槽位映射表 → 槽 7234 在节点 2
  3. 直接去节点 2 操作

  如果客户端去了节点 1：
    节点 1 返回 MOVED 7234 192.168.1.2:6379
    ← 「槽 7234 不在我这，去节点 2」
```

## 3. 哈希槽算法

### CRC16(key) % 16384

```python
def hash_slot(key: str) -> int:
    """计算 key 属于哪个槽"""
    return crc16(key.encode()) % 16384
```

### 计算结果

```
key           CRC16 % 16384    槽号    负责节点
───────       ────────────    ──────   ────────
user:1001     7234             7234     节点 2
user:1002     15231            15231    节点 3
product:50    3421             3421     节点 1
session:a1bc  12145            12145    节点 3
```

### 为什么是 16384？

| 因素 | 说明 |
|------|------|
| 数量级 | 16384 = 2^14，足够多节点使用（最多 1000 个节点） |
| 心跳消息大小 | 每个节点的槽位信息用 16384 bit 的位图表示 → 2KB |
| 效率 | 16384 的 CRC16 计算快，位图小，心跳轻量 |

> 16384 不是随意选的——它是平衡「粒度」和「性能」的结果。

### 一致性哈希 vs 哈希槽

| | 一致性哈希 | Redis Cluster 哈希槽 |
|--|-----------|-------------------|
| 原理 | 哈希环 + 虚拟节点 | 固定 16384 个槽位 |
| 数据分布 | 节点增减只影响少量 key | 节点增减需要手动迁移槽 |
| 实现复杂度 | 客户端实现 | 服务端 + 客户端配合 |
| 槽迁移 | 自动重新分布 | 手动或工具辅助 |
| 查询定位 | 客户端在环上查找 | 客户端缓存槽位表，或 MOVED 重定向 |

## 4. MOVED vs ASK 重定向

### MOVED — 槽确定不在我这

```
命令: GET user:1001

客户端去节点 1:
  节点 1 计算槽号 → 7234
  槽 7234 不在我负责的范围内
  → 返回 MOVED 7234 192.168.1.2:6379
  → 客户端更新本地槽位缓存，去节点 2 重试

（后续同 key 的操作直接去节点 2，不再需要重定向）
```

```
客户端                   节点 1                    节点 2
  │                       │                       │
  │── GET user:1001 ─────→│                       │
  │                       │  CRC16("user:1001")   │
  │                       │  = 7234 → 不是我的槽  │
  │←── MOVED 7234 :6379 ──│                       │
  │                       │                       │
  │  更新本地槽位映射表     │                       │
  │                       │                       │
  │── GET user:1001 ────────────────────────────→│
  │←── "小明" ───────────────────────────────────│
  │                       │                       │
```

### ASK — 槽正在迁移中

```
命令: GET user:1001

槽 7234 正在从节点 2 迁移到节点 3：

客户端去节点 3（本地缓存认为槽在节点 3）:
  节点 3：「槽 7234 是我负责的，但数据可能还在节点 2 那」
  → 返回 ASK 7234 192.168.1.2:6379
  → 客户端先发送 ASKING 命令获取临时访问权
  → 再去节点 2 读取数据

（迁移完成后，所有操作直接走节点 3）
```

### MOVED vs ASK 对比

| | MOVED | ASK |
|--|-------|-----|
| 含义 | 槽**已经**在另一个节点 | 槽**正在迁移** |
| 客户端操作 | 更新缓存，下次直接去新节点 | 先 ASKING，再去旧节点 |
| 持续时间 | 永久 | 迁移完成前临时状态 |
| 触发条件 | 槽已经不再当前节点 | 槽正在迁出 |

## 5. 集群故障转移

Cluster 中每个主节点可以有从节点，这和主从复制类似，但多了集群自动感知。

```
┌──────────┐    ┌──────────┐    ┌──────────┐
│ 主 1      │    │ 主 2      │    │ 主 3      │
│ 槽 0~5460 │    │ 槽 5461~ │    │ 槽 10923~│
│           │    │ 10922    │    │ 16383    │
└────┬─────┘    └────┬─────┘    └────┬─────┘
     │               │               │
     │ 主从复制       │ 主从复制       │ 主从复制
     ▼               ▼               ▼
┌──────────┐    ┌──────────┐    ┌──────────┐
│ 从 1      │    │ 从 2      │    │ 从 3      │
└──────────┘    └──────────┘    └──────────┘
```

### 主节点挂了会发生什么？

```
集群中其他主节点发现主 1 挂了
  → 投票（基于 Raft）
  → 把从 1 提升为新的主 1
  → 槽 0~5460 继续可用

整个过程对客户端基本透明
（除了主 1 刚挂到新主升起的短暂不可用）
```

### 集群故障 vs Sentinel 故障转移

| | Sentinel | Cluster |
|--|---------|---------|
| 监控范围 | 一组主从 | 所有节点互相监控 |
| 故障转移 | Sentinel 进程执行 | 集群主节点投票 + 从节点升级 |
| 配置 | 独立 Sentinel 配置 | 集群自带，无需额外组件 |
| 复杂度 | 简单，独立 | 集成但更复杂 |

## 6. 扩容/缩容 — 槽迁移

### 添加新节点

```
初始: 3 个节点，各约 5461 个槽

加入节点 4:
  1. CLUSTER MEET 192.168.1.4:6379  ← 加入集群
  2. 从现有节点迁移一些槽到节点 4
     CLUSTER SETSLOT 1000 NODE node4-id
  3. 迁移过程中，涉及 ASK 重定向

结果: 4 个节点，各约 4096 个槽
```

### 槽迁移过程

```
迁移前:
  节点 2: 负责 5461~10922，数据完整

迁移中:
  CLUSTER SETSLOT 7234 MIGRATING node2-id  ← 节点 2 标记迁出
  CLUSTER SETSLOT 7234 IMPORTING node3-id   ← 节点 3 标记迁入

  此时 key 在节点 2：
    客户端去节点 2 → 正常返回
    客户端去节点 3 → ASK 到节点 2

  数据迁移完成：
    CLUSTER SETSLOT 7234 NODE node3-id ← 槽归属切换

迁移后:
  节点 3: 负责 7234，数据完整
```

### 重新分片工具

```bash
# Redis 自带的在线重新分片工具
redis-cli --cluster reshard 192.168.1.10:6379
```

## 7. 常见错误

### ❌ 错误 1：多 key 操作跨槽

```redis
# 这两个 key 可能算到不同槽：
MGET user:1001 user:1002
# 如果它们在不同节点 → Redis 报错
```

> **CROSSSLOT** Keys in request don't hash to the same slot

**解决方案**：
1. 使用**哈希标签（hash tags）**强制相关 key 进入同一槽：

```redis
# {user} 是标签——CRC16 只计算 {} 内的内容
user:{1001}:profile
user:{1001}:orders

# 这两个 key 的槽号相同，可以一起操作
MGET user:{1001}:profile user:{1001}:orders
```

2. 应用层拆成多次操作。

### ❌ 错误 2：客户端不支持 MOVED

老旧的 Redis 客户端可能不处理 MOVED 重定向，直接报错。

> **使用支持 Cluster 模式的客户端**（如 `redis-py-cluster`、`lettuce`、`jedis` 等）。

### ❌ 错误 3：槽分配不均

```
节点 1: 9000 个槽
节点 2: 4000 个槽
节点 3: 3384 个槽
```

- 有些节点负载过高
- 影响集群整体性能

> **定期检查**：`redis-cli --cluster check 192.168.1.10:6379`
> **重新平衡**：`redis-cli --cluster rebalance 192.168.1.10:6379`

### ❌ 错误 4：所有节点挂在一个物理机上

```
❌ 3 个节点都在同一台服务器上
   → 服务器挂了，整个集群不可用

✅ 3 个节点分别在 3 台机器上
   → 任何一台机器挂了，集群还能服务（剩余主节点 + 从节点升主）
```

### ❌ 错误 5：跨数据中心的高延迟

Cluster 假设节点间低延迟网络。跨数据中心部署会导致：
- gossip 协议通信变慢
- 故障检测变慢
- 误判概率增加

> **建议**：每个数据中心内部署独立的 Cluster，上层通过其他机制同步。

## 8. 你学到了什么

| 概念 | 一句话 |
|------|--------|
| 哈希槽 | 16384 个槽，CRC16(key) % 16384 决定数据归属 |
| 分片 | 槽平均分布到多个节点，每节点负责一部分 |
| MOVED | 槽已经确定在另一个节点，客户端应更新缓存 |
| ASK | 槽正在迁移，客户端需要临时访问旧节点 |
| 哈希标签 | `{tag}` 让多个 key 落到同一槽，方便多 key 操作 |
| 集群故障转移 | 主节点挂了，从节点自动升主（Raft 投票） |
| 槽迁移 | 扩容/缩容时在线移动数据和槽归属 |
| 一致性哈希 vs 哈希槽 | Redis 选择哈希槽 = 更可控的数据分布 |

## 9. 自己动手

1. **搭建最小 Redis Cluster**（本地，不同端口）：
   ```bash
   # 创建 6 个实例（3 主 3 从），端口 7000~7005
   # 用 redis-cli --cluster create 创建集群
   redis-cli --cluster create 127.0.0.1:7000 127.0.0.1:7001 \
     127.0.0.1:7002 127.0.0.1:7003 127.0.0.1:7004 \
     127.0.0.1:7005 --cluster-replicas 1
   ```

2. **查看集群信息**：`CLUSTER INFO`、`CLUSTER NODES`、`CLUSTER SLOTS`

3. **计算槽号**：用 `CLUSTER KEYSLOT user:1001` 查看某个 key 的槽号

4. **模拟 MOVED**：在非负责节点上操作 key，观察 MOVED 重定向

5. **测试哈希标签**：用 `{tag}` 让多个 key 落到同一槽，执行 `MGET`

6. **模拟节点故障**：停掉一个主节点，观察从节点自动升主
