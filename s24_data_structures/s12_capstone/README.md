## 1. 本章工程问题

你学完了 11 个数据结构。每一个都做了 Mini 项目——但它们都是独立的。现在的问题是：

**这些数据结构能在同一个系统里协同工作吗？**

本章给你一个真实的系统骨架——**AI Agent 平台**——它需要用到前 11 章的数据结构。你的任务是把它们组装起来。

## 3. 每个数据结构在平台中的角色

| 模块 | 用的数据结构 | sXX | 在平台中的作用 |
|------|------------|-----|--------------|
| Workflow 引擎 | 图 + DAG | s11 | 编排 agent 任务的执行顺序 |
| 任务队列 | 队列 | s03 | 管理待执行的 agent 任务 |
| LLM 缓存 | 哈希表 | s05 | 相同问题不重复调 LLM |
| 用户记忆 | 树 | s04 | 按主题/时间存储对话记忆 |
| 搜索历史 | 倒排索引 | s10 | 全文搜索所有历史对话 |
| 版本管理 | 链表 + DAG | s01 | 记录 agent 配置的修改历史 |
| 操作撤销 | 栈 | s02 | undo/redo 操作历史 |
| Agent 评分 | 跳表 | s07 | agent 效果排行榜 |
| 对话索引 | B+ 树 | s09 | 按时间戳高效检索对话 |

### 数据流举例

```
用户: "帮我查一下上周和三菱商事的会议记录"

1. LLM 缓存 (s05): 查哈希表 → "这个问题之前没问过"
2. 搜索历史 (s10): 倒排索引查 "会议记录 三菱商事" → [doc3, doc7]
3. 对话索引 (s09): B+ 树范围查询 上周时间戳 → 过滤 doc3, doc7
4. Workflow 引擎 (s11): 拓扑排序编排执行流程
5. 任务队列 (s03): enqueue → fetch_docs → rank → generate_answer
6. 操作历史 (s02): push 到 undo 栈
7. 版本管理 (s01): commit 记录 "用户 #42 查询了会议记录"
```

## 6. 设计建议

### 不要试图一步到位

先让 1 个模块跑通，再加第二个。**骨架的价值在于模块之间的接口已经定义好了**——你不需要纠结「怎么设计架构」，只需要在模块内部填充逻辑。

### 数据类型要一致

所有模块共享同一个「对话记录」格式。建议定义一个标准的 `Message` 类型：

```python
@dataclass
class Message:
    id: str
    user: str
    content: str
    timestamp: float
```

所有模块（缓存、搜索、索引）都读写这个格式。

### 数据结构是真的在用

注意区别「Python 内置的」和「你自己实现的」：
- 用 `HashTable`（s05）做缓存——而不是 Python dict
- 用 `InvertedIndex`（s10）做搜索——而不是手写循环
- 用 `CommitChain`（s01）做版本——而不是 list

## 9. 本章总结 — 也是 s24 全部课程的总结

你从 s01 到 s12，走完了这条路：

```
链表 → 栈 → 队列 → 树 → 哈希表
  ↓
有序 vs 无序（过渡）
  ↓
跳表
  ↓
内存 vs 磁盘（过渡）
  ↓
B+ 树 → 倒排索引 → 图 + DAG
  ↓
综合项目（全部串联）
```

每一章你都在回答同一个问题：**「这个数据结构为什么要存在？」**

- 链表存在，因为数组的插入太慢
- 栈存在，因为后退按钮需要 LIFO
- 队列存在，因为消息系统需要 FIFO
- 树存在，因为文件系统是层级的
- 哈希表存在，因为 O(1) 存取太诱人
- 跳表存在，因为哈希表无法排序，有序数组插入太慢
- B+ 树存在，因为磁盘 IO 太贵，树必须矮
- 倒排索引存在，因为搜索引擎不能扫描全部文档
- 图存在，因为 Workflow 的依赖关系不是树的层级能表达的

**数据结构不是用来刷题的。数据结构是真实软件系统的骨架。** 你现在可以看着任何一个软件系统，问自己：「它的数据是怎么组织的？用了什么数据结构？为什么选这个？」

这就是 s24 的全部目标。
