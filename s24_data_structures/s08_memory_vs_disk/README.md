# s08: 内存 vs 磁盘 — ★ 为什么磁盘改变一切？

> *"在内存里，二叉树 20 次访问是 2 微秒。在磁盘上，20 次 IO 是 200 毫秒。同样的操作，慢了 10 万倍。你的数据结构必须为此重新设计。"*
>
> **前提知识**: 学过 s07（跳表），理解 O(log n)。不需要磁盘或操作系统知识。

---

## 1. 本章工程问题

s07 的跳表在内存里飞快。你现在接了一个新需求：

> **存储 10 亿条用户记录**，支持按 ID 快速查找。数据量太大，内存放不下。

你尝试把跳表存到磁盘上。结果令人崩溃：

```
在内存中（跳表）:
  查找 log₂(10亿) ≈ 30 次节点访问 × 100ns = 3 微秒 ✅

在磁盘上（同样的跳表）:
  查找 log₂(10亿) ≈ 30 次节点访问 × 10ms(每 IO) = 300 毫秒 ❌

慢了 100,000 倍！
```

**问题不在于跳表——问题在于你把「为内存设计」的数据结构直接搬到了磁盘上。**

---

## 2. 内存和磁盘的本质差异

| | 内存（RAM） | 磁盘（SSD/HDD） |
|------|-----------|----------------|
| 随机访问延迟 | ~100 纳秒 | ~10 毫秒（SSD） / ~10 毫秒 + 寻道（HDD） |
| 顺序访问 | 快 | 也很快（接近带宽上限） |
| 最小访问单位 | 1 字节 | 1 个 block（通常 4KB） |
| 价格/容量 | 贵 / 小 | 便宜 / 大 |
| 断电后 | 数据丢失 | 数据保留 |

### 关键数字

```
内存:   100 ns  = 0.0001 ms
磁盘:   10 ms   = 10,000,000 ns

差距 ≈ 100,000 倍

打个比方:
  内存访问 = 你去隔壁房间拿东西（1 秒）
  磁盘 IO  = 你从北京飞到纽约拿东西（1 天）
```

---

## 3. 为什么这个差异改变了数据结构的设计

### 在内存中：跳表很正常

```
查找 1 条记录 = 走 ~30 个节点
每个节点 = 1 次内存访问 = 100ns
总: 30 × 100ns = 3μs
```

节点分布在内存各处（指针指向哪就去哪）——**随机访问在内存里几乎免费**。

### 在磁盘上：同一个跳表，灾难

```
查找 1 条记录 = 走 ~30 个节点
每个节点 = 1 次磁盘 IO = 10ms
总: 30 × 10ms = 300ms
```

每个节点可能在不同的磁盘 block 里——**每次跟着指针走 = 一次随机 IO**。

### 关键洞察

> **磁盘擅长顺序读写，害怕随机读写。**

所以一个「磁盘友好」的数据结构应该：
1. **把相关数据放在一起**（一次 IO 读一个 block，block 里有几百个 key 最好）
2. **减少树的深度**（深度 = IO 次数）
3. **节点要大**（一个节点 = 一个 block = 一次 IO，节点越大利用率越高）

## 4. 磁盘模拟器演示

本章的 `disk_sim.py` 让你直观感受内存和磁盘的差距：

```python
class DiskSimulator:
    def read(self, block_id):
        """每次 read = 一次磁盘 IO"""
        self.io_count += 1
        time.sleep(self.io_delay)  # 模拟延迟
        return self._blocks.get(block_id)

# 统计: 一共做了多少次 IO？
```

### 二叉树 vs B+ 树的 IO 次数

```
1,000,000 条记录:

二叉树 (每个节点 1 个 key):
  深度 = log₂(1,000,000) ≈ 20 层
  每次查找 = 20 次节点访问 = 20 次 IO × 10ms = 200ms

B+ 树 (每个节点 500 个 key):
  深度 = log₅₀₀(1,000,000) ≈ 3 层
  每次查找 = 3 次节点访问 = 3 次 IO × 10ms = 30ms

速度差距: 200ms / 30ms ≈ 6.7x
```

> B+ 树没有发明新的算法——它只是让每个节点**更大**，从而让树**更矮**，从而减少 IO 次数。

## 5. 桥梁作用：引出 B+ 树

本章帮你建立了两个关键认知：

1. **磁盘和内存不是一个世界**——延迟差 10 万倍
2. **数据结构必须适配运行环境**——给磁盘设计的数据结构，核心目标是「减少 IO 次数」

s09 的 B+ 树就是这种适配的结果：

```
跳表 (为内存设计)          B+ 树 (为磁盘设计)
  每节点 1 个 key             每节点 100-500 个 key
  深度 log₂(n)                深度 log₅₀₀(n)
  随机指针到处飞              节点内部顺序扫描
  适合内存                    适合磁盘
```

## 7. 思考题

1. **SSD 和 HDD 的区别会改变数据结构的设计吗？** SSD 没有「寻道时间」，随机访问比 HDD 快很多。这是否意味着在 SSD 上二叉树就够用了？

2. **为什么操作系统每次读磁盘至少读 4KB？** 如果只读 1 字节会怎样？这和 B+ 树「大节点」的设计有什么关系？

3. **内存和磁盘之间还有一层：CPU Cache。** L1 Cache ~1ns, L2 ~10ns, RAM ~100ns, Disk ~10ms。数据结构的设计是否需要考虑 CPU Cache？

4. **如果数据全在内存里，还需要 B+ 树吗？** 数据库的「内存模式」（如 Redis）用跳表而不是 B+ 树——为什么？

5. **预测下一章**：s09 的 B+ 树每个节点存几百个 key。这对节点的内部结构（如何在节点内快速找到 key）提出了什么要求？

## 8. 本章总结

| 概念 | 一句话 |
|------|--------|
| 内存 vs 磁盘 | 延迟差 100,000 倍，随机 IO 是瓶颈 |
| IO 最小单位 | 磁盘按 block 读写（通常 4KB） |
| 关键指标 | IO 次数决定磁盘数据结构的性能 |
| 设计原则 | 减少深度 + 大节点 + 顺序访问 = 磁盘友好 |
| 跳表 vs B+ 树 | 跳表为内存设计（随机指针免费），B+ 树为磁盘设计（IO 是瓶颈） |

> **核心收获**：数据结构不是孤立的——它的设计取决于它运行的环境。一个在内存里优异的结构（跳表），搬到磁盘上可能变成灾难。s09 的 B+ 树就是专门为「数据在磁盘上」这个约束而生的。
