> *"冲突不是 Git 出错了。冲突是 Git 在问你：两边的改动不一样，你到底要哪个？"*
>
> **前提知识**: 理解合并（s05），知道 commit 是什么（s01）。

## 1. 为什么会有冲突？

Git 的自动合并能力很强，但有一个极限：**当两个分支修改了同一个文件的同一行时，Git 不知道该选哪个。**

```
main 分支改了 app.py 第 10 行:
    DEBUG = True

feature 分支也改了 app.py 第 10 行:
    DEBUG = False

Git: "两边都改了同一行，我不知道你想保留哪个。你自己来选。"
```

> **冲突不是 bug，是 Git 把决定权交给你**——因为只有你知道「正确的」版本是什么。

---

## 2. 在时间树模型下理解冲突

```
共同祖先（app.py 第 10 行 = "DEBUG = False"）
         │
    ┌────┴────┐
    │         │
main 改:    feature 改:
DEBUG = True   DEBUG = "verbose"
    │         │
    └────┬────┘
         │
    git merge feature
         │
    ⚠️ CONFLICT!
    Git: "main 说 DEBUG = True，feature 说 DEBUG = 'verbose'，我该听谁的？"

冲突发生的位置是「两条时间线对同一个东西给了不同的答案」。
```

---

## 3. 冲突标记详解

当冲突发生时，Git 会修改你的文件，插入冲突标记：

```
<<<<<<< HEAD                    ← 当前分支（你正在 merge INTO 的分支）的版本
DEBUG = True
=======                        ← 分隔线
DEBUG = "verbose"              ← 被合并分支（你要 merge 进来的分支）的版本
>>>>>>> feature-login          ← 被合并分支的名字
```

### 三段式结构

| 部分 | 含义 |
|------|------|
| `<<<<<<< HEAD` ~ `=======` | 你的当前分支的内容 |
| `=======` ~ `>>>>>>> branch` | 被合并分支的内容 |
| `>>>>>>> branch` | 冲突块结束 |

> **如果有多个冲突**，文件中会出现多个这样的标记块。

---

## 4. 解决冲突 — 三步法

### 第 1 步：找到冲突文件

```bash
git status
# Unmerged paths:
#   both modified:   app.py
```

### 第 2 步：打开文件，决定保留哪边

```python
# 选项 A: 保留当前分支的
DEBUG = True

# 选项 B: 保留被合并分支的
DEBUG = "verbose"

# 选项 C: 两边都保留（合并）
DEBUG = True  # 生产环境
DEBUG_LEVEL = "verbose"  # 开发环境

# 选项 D: 写一个全新的
DEBUG_MODE = "production"
```

删除冲突标记 `<<<<<<<`、`=======`、`>>>>>>>`，保留你想要的代码。

### 第 3 步：标记为已解决 + 提交

```bash
git add app.py                    # 标记冲突已解决
git commit -m "合并 feature-login，解决 DEBUG 配置冲突"
# 或者直接用:
git commit                        # Git 会自动生成 merge commit 信息
```

> 不需要 `-m` 也可以！Git 会打开编辑器，预设信息为 "Merge branch 'xxx' into main"。直接保存退出即可。

---

## 5. 取消合并 — 后悔药

```bash
git merge --abort
```

如果合并到一半发现「算了，不合并了」，用 `--abort` 回到合并前的状态。工作区和暂存区都会恢复。

---

## 6. 预防冲突的策略

| 策略 | 说明 |
|------|------|
| **小步提交** | commit 越小，冲突的可能性越小 |
| **频繁合并主分支** | `git merge main` 到你的 feature 分支——不要攒 3 天再合并 |
| **沟通** | 改同一个文件之前，跟队友说一声 |
| **拆文件** | 不要把所有代码写在一个巨大的文件里 |

## 7. 常见错误（新手必读）

### ❌ 错误 1：看到冲突标记就慌，不敢改

```
<<<<<<< HEAD     ← "这是什么？完了，我的代码坏了！"
```

> 冲突标记是 Git 在帮你！它精确告诉你两边的差异在哪。读清楚，做选择，删掉标记。

### ❌ 错误 2：没删干净标记就 commit

```python
DEBUG = True
<<<<<<< HEAD      # ❌ 忘了删标记！
```

> commit 前用 `git diff --staged` 确认没有残留的 `<<<<<<<` 或 `>>>>>>>`。

### ❌ 错误 3：解决冲突后没有 add 就 commit

```bash
# 编辑完冲突文件
git commit -m "merged"    # ❌ 冲突还没标记为已解决
# nothing to commit
```

> **规则**：解决冲突后，必须 `git add` 告诉 Git「我处理好了」。

### ❌ 错误 4：不敢合并，怕出冲突

> 冲突是正常的，不是灾难。处理冲突 = Git 使用者的基本功。越怕越不会，越不会越怕。

## 8. 你学到了什么

| 概念 | 一句话 |
|------|--------|
| 冲突的本质 | 两个分支改了同一行，Git 不知道选哪个 |
| 冲突标记 | `<<<<<<<` / `=======` / `>>>>>>>` 三段式标记 |
| 解决冲突 | 打开文件 → 选择/修改 → 删标记 → `git add` → `git commit` |
| `git merge --abort` | 取消合并，回到合并前状态 |
| 预防冲突 | 小步提交、频繁合并主分支、团队沟通 |

## 9. 自己动手

1. **故意制造冲突**：在 main 和 feature 分支上改同一个文件的同一行，然后合并——看冲突标记长什么样
2. **尝试三种解决方案**：保留 main 的、保留 feature 的、自己写一个新的
3. **制造多文件冲突**：在 3 个文件里都制造冲突，练习逐个解决
4. **用 `git merge --abort`** 在冲突中取消合并
5. **解决冲突后用 `git log --graph`** 看 merge commit 的结构
