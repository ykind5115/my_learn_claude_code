## 1. 没有版本控制的痛苦

先回忆一下：你是怎么管理文件版本的？

```
论文_v1.docx
论文_v2.docx
论文_v2_导师修改.docx
论文_v3.docx
论文_v3_最终版.docx
论文_v3_最终版_真的最终版.docx
论文_v3_最终版_真的最终版_再也不改了.docx
```

这个方案的致命问题：

| 问题 | 为什么痛苦 |
|------|-----------|
| **不知道改了哪里** | "v3 比 v2 到底改了什么？"——只能人工对比 |
| **找不到某个版本** | "去年 3 月那个版本还在吗？"——可能早就被覆盖了 |
| **不敢删旧版本** | "万一下次要回退呢？"——硬盘越堆越满 |
| **多人协作更惨** | "你改的和我改的怎么合到一起？"——手动合并 = 灾难 |

**代码开发的版本管理比论文更复杂**：
- 一个项目有几十上百个文件，不是单个 docx
- 多人同时改同一个文件是常态
- 你需要频繁在「开发新功能」和「修复线上 bug」之间切换
- 出问题了要能精确回到「昨天的下午 3 点的那个状态」

## 2. Git 的核心思想：快照，不是差异

大多数版本控制工具（比如 SVN）存储的是**文件之间的差异（delta）**：

```
SVN 的方式:
  v1: 文件完整内容 (100KB)
  v2: 只存储「v1 → v2 改了哪 3 行」(2KB)
  v3: 只存储「v2 → v3 改了哪 5 行」(3KB)
  ...
  要拿到 v5？从 v1 开始应用 v2 的差异，再应用 v3 的差异...累积计算。
```

**Git 的方式完全不同**——它存储的是**每个版本的文件完整快照（snapshot）**：

```
Git 的方式:
  v1: 整个项目的完整快照
  v2: 整个项目的完整快照（改过的文件存新版本，没改的文件直接引用 v1 的）
  v3: 整个项目的完整快照
  ...
  要拿到 v5？直接取出 v5 的快照，不用计算。
```

> **这就像拍照 vs 录像**：
> - SVN 是录像——你要看 5 分钟前的画面，得从那个时间点开始播放
> - Git 是相册——你要看 5 分钟前的画面，直接翻到那一页

这个设计带来了 Git 的核心优势：**任何操作都极快**。因为切换版本不用计算差异，直接取出完整快照就行。

## 3. 时间树：Git 的心智模型

Git 把你的项目历史组织成一棵**树**（严格说是有向无环图 DAG，但先当成树来理解）：

```
时间 →

    ○  ← commit A
    │     "第一次提交：创建了 index.html"
    │
    ○  ← commit B
    │     "加了导航栏"
    │
    ○  ← commit C
    │     "改了背景颜色"
    │
    ●  ← 最新的 commit（你现在在这里）
          "修复了一个拼写错误"
```

### 核心概念 1：commit = 时间线上的一个节点

每次 `git commit`，就像在时间线上**种下一个节点**。这个节点记录了：
- 整个项目在那一刻的完整快照
- 是谁提交的、什么时候
- 提交信息（"我做了什么"）
- **指向前一个节点的指针**（这样就形成了链）

```
每个 commit 节点:

┌─────────────────────────────┐
│  Commit                      │
│  ├── 快照: 所有文件的内容     │
│  ├── 作者: zhangsan          │
│  ├── 时间: 2026-06-29 15:30  │
│  ├── 信息: "修复拼写错误"     │
│  └── parent: → 指向上一个节点 │
└─────────────────────────────┘
```

### 核心概念 2：branch = 贴在节点上的可移动标签

分支（branch）不是「一条线」——它只是**贴在某一个 commit 节点上的标签**。

```
想象这个:

    ○  ← commit A
    │
    ○  ← commit B
    │
    ○  ← commit C  ← [main]  标签 "main" 贴在这里
    │
    ●  ← commit D  ← [feature-login]  标签 "feature-login" 贴在这里

main 和 feature-login 都是标签。
当你做新 commit 时，当前标签会自动跟你一起移动。
```

> **把分支想象成便利贴**：
> - 你可以把便利贴贴在时间线的任意节点上
> - 便利贴可以撕下来贴到别处
> - 当你「站在」某个便利贴上做新 commit，便利贴自动跟你走
> - 一个节点上可以贴多个便利贴

这就是为什么 Git 的分支**极快**（几毫秒）——它只是在创建一个新标签，不需要复制任何文件。

### 核心概念 3：HEAD = 「你现在站在哪」

`HEAD` 是一个特殊的指针，指向**你当前所在的节点**。

```
    ○  ← commit A
    │
    ○  ← commit B  ← HEAD → main
    │
    ○  ← commit C

HEAD 指向 main，main 指向 commit B → 你在 commit B 这里
```

大多数时候，HEAD 指向一个分支名（表示你在这个分支上）。当你 `git checkout` 其他分支时，HEAD 就移动。

> **HEAD 就像你的「当前位置」光标**——你在时间树的哪里，HEAD 就在哪里。

### 核心概念 4：merge = 两条时间线汇合

当你把 `feature-login` 分支合并回 `main`：

```
合并前:
    ○───○───○  ← main
         └───●  ← feature-login

合并后:
    ○───○───○───●  ← main（合并节点，有两个 parent）
         └───●───┘

合并节点是一个特殊的 commit——
它有「两个 parent」（来自 main 的一条线和来自 feature-login 的一条线）。
```

## 4. 三个区域：工作区、暂存区、仓库

Git 把你的项目分成**三个区域**：

```
┌──────────────┐    git add    ┌──────────────┐   git commit   ┌──────────────┐
│   工作区      │  ──────────→  │   暂存区      │  ───────────→  │   仓库        │
│  Working      │              │  Staging      │               │  Repository   │
│  Directory    │              │  Area         │               │  (.git)       │
│              │  git restore  │              │               │              │
│  你正在编辑   │  ←──────────  │  准备拍照的   │               │  历史快照     │
│  的文件       │              │  文件列表     │               │  的集合       │
└──────────────┘              └──────────────┘               └──────────────┘
     📝                          📸                            📚
```

| 区域 | 类比 | 里面有什么 |
|------|------|-----------|
| **工作区** | 你的书桌 | 你正在写、正在改的文件。Git 以外的普通文件。 |
| **暂存区** | 准备拍照的队列 | 你决定「下一张快照要包含哪些改动」。可以选择性添加。 |
| **仓库** | 相册 | 所有历史快照的集合。`.git/` 目录里的一切。 |

### 为什么要有暂存区？

这是 Git 设计中最天才的地方之一。暂存区让你**可以选择性地提交**：

```
你改了 3 个文件:
  - index.html   (加导航栏 —— 完成了)
  - style.css    (改背景色 —— 完成了)
  - app.js       (修复 bug —— 还在调试中)

你可以只把 index.html 和 style.css 加入暂存区并提交，
app.js 留到下次再提交。

这就叫"逻辑上相关的改动放在同一个 commit 里"。
```

> 没有暂存区的版本控制工具，要么全部提交，要么全部不提交——失去了精细控制。

## 5. 一张总图：你脑子里的地图

把上面所有概念拼在一起，就是这张图。**带着这张图去学后面的每一章**：

```
工作区                      暂存区                        仓库（时间树）
┌──────────┐   git add    ┌──────────┐   git commit    ┌─────────────────┐
│ index.html│ ──────────→ │ index.html│ ─────────────→ │                  │
│ style.css │             │ style.css │               │  ○ ← commit A    │
│ app.js    │             │           │               │  │               │
│           │             │           │               │  ○ ← commit B    │
│           │             │           │               │  │               │
│           │             │           │               │  ○ ← main (HEAD) │
│           │             │           │               │  │               │
│           │             │           │               │  ● ← feature     │
└──────────┘             └──────────┘               └─────────────────┘
    📝                       📸                            📚

    git restore          git restore --staged
    ←────────────────   ←────────────────────
    (丢弃工作区改动)     (从暂存区撤出)
```

## 6. 一个操作的完整旅程

以「修了一个 bug，提交到仓库」为例，用时间树模型来理解整个过程：

```
Step 1: 你在编辑器里改了 app.js
        → 工作区有了改动

Step 2: git add app.js
        → 把改动从工作区复制到暂存区（「这张照片要包含 app.js」）

Step 3: git commit -m "修复登录按钮不响应的问题"
        → Git 做 5 件事：
          ① 给所有暂存区的文件拍一张快照
          ② 创建一个 commit 节点（包含快照 + 元信息 + 指向前一个节点的指针）
          ③ 把新节点挂在时间线上
          ④ 把当前分支标签移到新节点上
          ⑤ 清空暂存区

完成后的时间树:
    ○ ← commit A  "之前的提交"
    │
    ● ← commit B  "修复登录按钮不响应的问题"  ← main (HEAD)
```

## 7. 进入实操之前

下一章（s01）你将在终端里执行真正的 git 命令。在此之前，回顾一下你的「地图」：

| 概念 | 一句话 |
|------|--------|
| Git | 给项目拍快照的工具 |
| commit | 时间线上的一个节点（一次快照） |
| branch | 贴在节点上的可移动标签 |
| HEAD | 「你现在站在哪个节点上」的指针 |
| merge | 让两条时间线汇合 |
| 工作区 | 你正在编辑的文件（书桌） |
| 暂存区 | 准备下一次提交的文件列表（拍照队列） |
| 仓库 | 所有历史快照的集合（相册，藏在 .git/ 里） |

> 如果你暂时没完全理解暂存区和分支的区别，**完全没关系**。
> s00 的任务只是让你知道「有这么一张地图存在」。
> 后面每一章会反复回到这张图，你会越来越清晰。
